The FDE Mindset

Skills tell you how to build; mindset tells you what to do when the problem is vague, the customer is waiting and something just broke. Learn the seven habits of thinking that great FDEs share.

Seven habits of thinking

The good auto driverTwo drivers know the same roads. One drops you at the main gate and says “my job is done”. The other asks which building, finds a shortcut when the road is blocked, and waits until you are actually inside. Same skills, different mindset, and only one of them solved your problem.

The previous note listed what an FDE does. This note is about how an FDE thinks while doing it. We will use one running example throughout: ABC Bank, which wants AI to help with loan applications and customer questions.

1 · Ownership

Ownership means taking responsibility for solving a customer’s problem from start to finish. An FDE does not think “I only need to finish my assigned task.” An FDE thinks “I need to make sure the customer’s problem is actually solved.”

  1. 1
    Responsibility from discovery to solutionStay involved from understanding the problem until the solution works in production. → understand → build → deploy → fix problems
  2. 2
    Own technical decisions and implementationTake responsibility for how it is built: which API, database connection or AI model to use.
  3. 3
    Follow problems until they are resolvedIf something breaks, don’t just pass it on. → API fails → find the cause → fix it → test again
  4. 4
    Own outcomes, not just tasksDon’t just build a chatbot; make sure it actually reduces the customer-support workload.
  5. 5
    Coordinate product, engineering and customer teamsCustomer explains the issue → FDE works with product and engineering → solution is built → FDE reports back to the customer.

2 · Handling ambiguity

Ambiguity means the problem or requirements are not completely clear. Customers say things like “We need AI to make this faster” without saying exactly what to build. The FDE works out what they really need and keeps moving even when some information is missing.

Work with unclear requirements

Customers may not know what they want technically. Start with what you have and work toward the missing pieces.

Ask to find the real problem

Ask before building: “Which part of the process is slow?” “Who is using the system?”

Make reasonable assumptions

Waiting for every detail stalls a project. Assume sensibly, say the assumption out loud, and continue.

Name unknowns and risks

“We don’t know if the customer’s API can handle 1,000 requests per minute.”

Break it into small problems

“Build AI assistant” → understand data → connect API → test AI → deploy assistant.

Iterate as you learn

The first solution need not be perfect. Build, learn, improve.

Ambiguity in one line Don’t get stuck because the problem is unclear. Ask, assume carefully, break it down, and keep learning as you go.

3 · Speed

Speed means solving and testing customer problems quickly without wasting time: understand → build something small → get feedback → improve. Speed does not mean careless or unreliable code.

HabitExample
Move quickly from understanding to experimentingCustomer wants AI document processing → test it on 20 sample documents
Do the most important technical work firstCheck the AI can extract data correctly before building the full app
Build small prototypes before big implementationsA simple chatbot before the full production system
Avoid unnecessary early complexityOne API and one data source, not 10 systems on day one
Get feedback quicklyCustomer tries the chatbot: “It also needs to answer loan-status questions.”
Balance speed with reliability and qualityA prototype can have basic error handling; production needs proper security, testing and monitoring

Instead of spending 2 months building everything for ABC Bank’s loan assistant:

Fast is right for…

Careful is right for…

The production system: security, testing, monitoring, maintainable code.

Speed in one line Build small → test fast → get feedback → improve → then build big.

4 · Technical depth

Technical depth means understanding how a system actually works, not just how to use it. Not just “the API is failing”, but why it is failing and how to fix it.

  1. 1
    See beyond the surfaceDon’t only call an API; understand how it connects to the backend and database.
  2. 2
    Strong engineering fundamentalsProgramming, data structures, APIs, databases, testing and system design, so solutions are reliable and maintainable.
  3. 3
    Debug complex problemsAI response is slow → check API → database → network → model → find the bottleneck.
  4. 4
    Know how the pieces connectCustomer app → API → backend → database → cloud.
  5. 5
    Find root causes“The application is slow” → one database query takes 8 seconds.
  6. 6
    Make informed decisionsChoose based on real requirements and constraints, e.g. use an existing API instead of building a new system from scratch.
  7. 7
    Know when to go deeperA small UI glitch may be simple; a data-security issue deserves a much deeper investigation. Go deep when reliability, performance, security or the customer outcome is at stake.

5 · Business understanding

Business understanding means knowing how the customer’s business works and what business result they need. An FDE thinks beyond code: why does the customer need this, and what should be better afterwards?

Business context

What the customer does, who their users are, how they operate. For a bank: how loan applications are processed.

Tech → business impact

Slow API → loan processing takes longer → customers wait longer.

Workflows & operational processes

The steps people follow to complete a business task. Customer submits loan → employee checks documents → employee verifies data → loan is processed.

Requirements & constraints

“Process loans faster, but customer data must remain secure.”

The outcome needed

“What should be better after we build this?” Loan processing from 2 days to a few hours.

Measurable objectives

AI document processing → less manual work → faster loans → better customer experience.

Example: “We need an AI system for loan processing”

The FDE does not start building AI immediately. First, the business:

Business problem: loans take 2 daysWhy? Employees read documents by handTechnical opportunity: AI extracts the informationBusiness outcome: shorter processing time

Now the FDE can state a clear objective: “Build an AI document-processing system that reduces manual data entry and helps decrease loan processing time.”

6 · Customer empathy

Customer empathy means understanding the customer’s situation from their point of view, not just the engineer’s: what users need, what problems they face, what constraints they have, and then building something truly useful and practical for them.

The tailor, not the shopA readymade shirt is built for “everyone”. A good tailor measures you, asks how you’ll wear it and adjusts after the trial. Empathy is the tailor’s habit.
  • Understand the customer’s perspective. Not only “How do I build this?” but “What is the customer trying to achieve, and why does it matter to them?”
  • Listen carefully. Don’t rush to suggest technology. Hear their concerns about cost, speed, security, usability and reliability.
  • Understand workflows and pain points. How do users work today, and where do they struggle? E.g. customer submits document → employee checks it manually → data entered → approval.
  • Explain technical ideas simply. Non-technical users may not know “API”, “latency”, “embeddings”, “Kubernetes” or “vector database”. Use plain business language.
  • Respect the customer’s constraints and environment. Their budget, existing tools, team skills, security rules and infrastructure shape what is practical.
  • Adjust based on real feedback. The first version won’t be perfect; show it, collect feedback, and change it to fit what users actually need: Build → Show → Listen → Improve.
  • Build practical solutions. Don’t build something impressive just because you can. Build what the customer can use, maintain, operate and get value from.

Example: listening to loan officers

Talking to ABC Bank’s loan officers, the FDE hears: “The AI is not the main problem. We spend hours manually checking customer documents.” So the FDE observes their workflow and proposes a change. After seeing a prototype, employees ask for human review before anything is submitted, so the final design includes it.

Empathy in one line Understand the customer → listen to their problems → understand their environment → build what actually works for them.

7 · Bias toward action

Bias toward action means not getting stuck in endless discussion or waiting for perfect information. Take what you know, start with a small action, test it, learn from the result, and keep moving.

HabitWhat it looks like
Turn problems into concrete next stepsNot “The system is too slow” but “Let’s measure the API response time and find which part is slow.”
Start with available informationUse what you know, make reasonable assumptions, start investigating
Test assumptions through experimentsThink the AI can read invoices? Test it on 20 real invoices
Build prototypes to answer uncertain questionsA small prototype answers “Can this actually work?”
Learn from results and adjustA failed experiment is useful information. Change the approach and try again
Move from discussion to implementationInstead of a week of meetings, build a small version and show the customer

Example: “Automatically process loan documents”

Instead of weeks of debate about which AI model to use, the FDE identifies the key question, “Can AI extract the required data?”, and tests it:

Customer problemKey question20 sample documentsSmall prototypeTest accuracyShow customerFeedbackImproveProduction system

The FDE acts early, learns from real results, and then makes better technical decisions.

Action ≠ rushing Bias toward action is about small, safe experiments. It is not an excuse to skip discovery or push untested code to production.

Key terms

Ownership
Taking responsibility for a customer’s problem from discovery until the solution works in production, and caring about the outcome rather than just finishing tasks.
Ambiguity
A situation where the problem or requirements are not fully clear; FDEs handle it by asking questions, making stated assumptions and breaking the problem down.
Reasonable assumption
A sensible guess made when information is missing, clearly communicated to the customer, so work can continue without waiting for every detail.
Speed (FDE sense)
Moving quickly from understanding to a small tested prototype and feedback, while keeping the final production system secure and reliable.
Technical depth
Understanding how a system works beneath the surface well enough to debug it and find the root cause of a problem.
Bottleneck
The single slowest part of a system that limits its overall speed, such as one database query taking 8 of 10 seconds.
Business understanding
Knowing how the customer’s business works and linking technical work to a measurable business result.
Customer empathy
Seeing a problem from the customer’s and users’ point of view and designing around how they actually work.
Bias toward action
Preferring a small, concrete experiment over endless discussion or waiting for perfect information.
