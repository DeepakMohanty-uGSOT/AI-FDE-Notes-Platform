HTML Basics: Forms and Inputs

Build forms that collect information from users: text boxes, choices and buttons, wired up with name and value, organised with labels and fieldsets, and guarded by built-in validation.

The <form> tag: the master envelope

The India Post envelopeYou put several sheets of paper into one envelope, write the To: address on it, and choose how to send it. The <form> tag is the envelope that wraps all the fields and tells the browser where and how to send them.

By itself <form> is invisible. It is a management tool: it wraps the fields (<input>, <textarea> and so on) and tells the browser two critical things:

action · WHERE

The address the data is sent to: the “To:” on the envelope.

method · HOW

How the data is sent (GET or POST). Covered in detail in an upcoming module.

<form action="/submit-contact-form"> …fields and a submit button… </form>

action · the attribute name

the server address that receives the data

the controls the user fills in

<form action="/submit-contact-form">
  <input type="submit" />
</form>

This means: “When the user clicks Submit, send all the form data to /submit-contact-form on the server.” Click it and watch the address bar:

Coming later Don’t worry about the method attribute yet; we will discuss it in an upcoming module.

More form attributes: target and enctype

target: where does the reply open?

When you post a letter (submit the form), the server writes back. target decides where that reply opens.

target="_self" (default)

Open the result in the same tab. The current page is replaced, e.g. a welcome page after login.

target="_blank"

Open the result in a new tab or window. The form page stays open, e.g. a “Thank you” page in a new tab.

<form action="/login" method="POST" target="_self">
  ...
</form>
<form action="/subscribe-thanks" method="POST" target="_blank">
  ...
</form>

enctype: how is the data packed?

enctype (encoding type) tells the browser how to pack the form data before sending it, like choosing how to wrap a parcel. Imagine you’re sending a package: most of the time you just put paper documents in an envelope, simple and light. But a photo or a gift needs a bigger box and a different label.

ValueMeaningUse when
application/x-www-form-urlencoded (default)Normal wrapping: all fields become one long text string.Text, passwords, simple data. Cannot send files.
multipart/form-dataSpecial packaging: the form is split into separate parts, one per field, including files.Only when the form has <input type="file"> (and method="POST").
profile picture upload
<form action="/upload-profile-pic" method="POST" enctype="multipart/form-data">
  <label for="username">Username:</label>
  <input type="text" id="username" name="user_name">

  <label for="profile-pic">Picture:</label>
  <input type="file" id="profile-pic" name="user_pic">

  <button type="submit">Upload</button>
</form>

Output:

After you submit the form, open DevTools → Network tab, click the request, and look at Request Headers: the enctype appears as the Content-Type header.

Text takers: the “fill in the blank” crew

If <form> is the envelope, the controls are the fields you fill in and the button you press. The most powerful is <input>, a chameleon whose type attribute changes what it becomes.

1 · <input type="text">

The default, most basic single-line text box: a simple rectangle to type in.

<input type="text">

2 · <input type="password">

A single-line box that hides what you type, showing dots (••••••••) instead of the characters.

<input type="password">
Hidden is not secure type="password" only hides the text on screen from people looking over your shoulder. The value is still sent as normal text, so real security needs HTTPS and careful handling on the server. On its own it gives basic privacy, not full security. Don’t worry: we will discuss how to make passwords fully secure in upcoming modules.

3 · <input type="email">

Looks like a normal text box but is smarter: on submit the browser checks that the text looks like an email address (something, then @, then a domain). On mobile, the keyboard shows the @ key.

<input type="email" required>

The required attribute stops the form from being submitted while the box is empty (more in the validation section).

4 · <textarea>

For long text (paragraphs, messages, feedback): a large, resizable box. Unlike <input>, it has a closing tag.

<textarea rows="5" cols="30"></textarea>
  • rows="5" sets the height: how many lines tall.
  • cols="30" sets the width: how many characters wide.

The three key attributes: id, value, name

1 · id: the unique identifier

A unique, one-of-a-kind nickname for one element on the page, like a student ID number: no two students share one. We use it to connect a <label> to an input, and to find or style that element with CSS or JavaScript.

<label for="userEmail">Email:</label>
<input type="email" id="userEmail">

The label’s for="userEmail" matches the input’s id="userEmail", so clicking the text “Email:” puts the cursor in the email box. (The <label> tag gets its own section below.)

2 · value: the answer

value is the actual data in the field: what you write on the blank line of an order slip. It is for the server. It works in two ways:

Fields you type in

For text inputs, value is pre-filled default text. The user can keep it or type something new. Whatever is in the box on submit is sent.

Fields you click

For radio buttons and checkboxes the user can’t type, so you must set value. It is the hidden answer sent if that option is chosen.

Type A: fields you type in · value is pre-filled text

pre-filled text
<label for="city">City:</label>
<input type="text" id="city" name="city" value="New York">

The user sees a box that already has “New York” in it. They can leave it or type something new. Whatever is in the box when they hit Submit is the value.

Type B: fields you click · value is the hidden answer

hidden answer
<label for="size-lrg">Large</label>
<input type="radio" id="size-lrg" name="size" value="L">

The user sees “Large” (from the label), but if they click it, the value sent is L: the hidden, pre-defined answer for the server. value is the “answer” that gets sent.

3 · name: the label on the data

The kitchen order slipThe input is the blank box on the slip, the value is what you write (“Cheeseburger”), and the name is the title printed above the box (“MainCourse”). The kitchen doesn’t just receive “Cheeseburger”; it receives MainCourse=Cheeseburger.
one field has a name, one doesn’t
<form action="/kitchen-order" method="POST">
  <label for="food">Main Course:</label>
  <input type="text" id="food" name="MainCourse" value="Cheeseburger">

  <label for="drink">Drink:</label>
  <input type="text" id="drink" value="Lemonade">

  <input type="submit" value="Send to Kitchen">
</form>
  1. 1
    First fieldThe browser sees name="MainCourse" and value="Cheeseburger", and writes MainCourse=Cheeseburger.
  2. 2
    Second fieldIt sees value="Lemonade" but no name. The kitchen wouldn’t know what this is for, so the browser throws it away.
  3. 3
    What the server receivesOnly MainCourse=Cheeseburger. The server never finds out about the Lemonade. → no name = no data
Most common form bug A field without a name looks perfectly fine on screen but sends nothing. If the server says a value is missing, check the name first.

Choice makers: radio, checkbox, select

1 · <input type="radio">: pick only one

Round buttons used in a group when the user must pick exactly one, like the preset buttons on an old car radio: press one and the other pops out.

AttributeJob
type="radio"Draw a round button.
name="size"The magic part: all radios with the same name form one group, so only one can be chosen.
value="lrg"The answer sent to the server. The user sees the label (“Large”); the server gets the value.
id="size-l"Unique nickname, used to link a <label>.
checkedMakes this option the default choice when the page loads.
name="size" links all three
<p>Choose your size:</p>

<label for="size-s">Small</label>
<input type="radio" id="size-s" name="size" value="sml">

<label for="size-m">Medium</label>
<input type="radio" id="size-m" name="size" value="med" checked>

<label for="size-l">Large</label>
<input type="radio" id="size-l" name="size" value="lrg">

If the user picks “Large” and submits, the server receives size=lrg.

2 · <input type="checkbox">: pick any

Square boxes for picking as many options as you like (or none), like ticking items off a shopping list. The attributes are the same as radio, but name now means a category: three ticked boxes named topping send three answers for “topping”. value is sent only if that box is ticked.

name="topping" groups them as one question
<p>Choose your toppings (select any):</p>

<label for="top-pep">Pepperoni</label>
<input type="checkbox" id="top-pep" name="topping" value="pep">

<label for="top-olives">Olives</label>
<input type="checkbox" id="top-olives" name="topping" value="olv" checked>

<label for="top-cheese">Extra Cheese</label>
<input type="checkbox" id="top-cheese" name="topping" value="x-chz" checked>

Submitted as-is (Olives and Extra Cheese ticked), the server receives topping=olv and topping=x-chz.

3 · <select> and <option>: the dropdown

A dropdown menu for a long list of options that would take too much space as radios. It works like a rolled-up scroll: click the <select> to unroll it, see all the <option>s, pick one, and it rolls back up showing only your choice.

On <select> (the box)

name · the question sent to the server, e.g. user_country.
id · links to a <label>.

On <option> (the choices)

value · most important: the answer sent. Users see the text between the tags (“United States”); the server gets the value (“USA”).
selected · the default choice.

country dropdown
<label for="country-select">Choose your country:</label>
<select id="country-select" name="user_country">
  <option value="">--Please select--</option>
  <option value="USA">United States</option>
  <option value="CAN">Canada</option>
  <option value="UK" selected>United Kingdom</option>
</select>

Left on the default, the server receives user_country=UK; changed to Canada, it receives user_country=CAN.

Where name lives On radios and checkboxes, name goes on every input in the group. On a dropdown, name goes once on the <select>, and value goes on each <option>.

The “do something” buttons

1 · <input type="submit">: the Send button

The most important button: it gathers all the form data and sends it to the server, like the “Place Order” button on the order slip. Its value is the text on the button: value="Log In" makes a button that says “Log In”.

<form action="/login" method="POST">
  <label for="user">Username:</label>
  <input type="text" id="user" name="username">
  <input type="submit" value="Sign Me Up!">
</form>

2 · <input type="reset">: the Clear button

Instantly erases everything typed into the form and returns every field to its default state (usually blank), like the “shake to clear” of an Etch A Sketch: all your hard work is gone, leaving a blank slate. It sends nothing. Its value is the button text, e.g. “Start Over”.

<form action="/signup" method="POST">
  <label for="user">Username:</label>
  <input type="text" id="user" name="username">
  <br>
  <label for="pass">Password:</label>
  <input type="password" id="pass" name="password">
  <br><br>
  <input type="submit" value="Sign Up">
  <input type="reset" value="Clear Form">
</form>

3 · <button>: the modern button

<input type="submit"> is a ready-made button: you can only change its text. <button> is a custom button: you can put HTML inside it (text, icons, images, bold words). We use <button> because it gives us more freedom to design buttons the way we want.

the old way: just text
<input type="submit" value="Submit Your Order">
the modern way: anything inside
<form action="/order" method="POST">
  ...
  <button type="submit">
    <img src="cart-icon.png" alt="" width="16">
    <b>Place Your Order</b>
  </button>
</form>
Always write type on <button> Inside a form, a <button> without a type acts as submit. Use type="submit", type="reset" or type="button" (does nothing by itself) so your intent is clear.

The <label> tag: the leash

<label> is the official way to describe a form field. It isn’t just plain text: it is linked to its field. If the input is a dog, the label is its leash.

The link is made by two attributes that must match: for on the label and id on the input.

<label for="user_email">Your Email:</label>
<input type="email" id="user_email" name="email_address">

for="user_email" on the label…

…matches id="user_email" on the input

the visible description

✅ right way
<form>
  <label for="user_email">Your Email:</label>
  <input type="email" id="user_email" name="email_address">
</form>
❌ wrong way (never do this)
<form>
  <p>Your Email:</p>
  <input type="email">
</form>

The wrong way looks the same, but it is just plain text with zero benefits.

Usability

Clicking the label text moves the cursor into the box. A big help for tiny checkboxes and radio buttons.

Accessibility

Screen readers announce “Email, input box” instead of just “input box”.

Golden rule Every input gets a <label>, connected with for and id. This makes your form easier to use and accessible for everyone. (You can also wrap the input inside the label, <label><input …> Small</label>, which links them without for/id.)

Grouping with <fieldset> and <legend>

<fieldset> and <legend> group related fields together and give the group a title: <fieldset> makes a box around related inputs, and <legend> gives that box a heading.

If a form is a long sheet of paper, a <fieldset> draws a border around one section (like “Contact Info”), and the <legend> is the title written at the top of it.

  • <fieldset> wraps a group of related labels and inputs. Most browsers draw a thin border around it.
  • <legend> must be the first thing inside the fieldset. Browsers place it on top of the border line.
two sections
<form>
  <fieldset>
    <legend>Contact Information</legend>
    <label for="name">Name:</label>
    <input type="text" id="name" name="name">
    <br>
    <label for="phone">Phone:</label>
    <input type="tel" id="phone" name="phone">
  </fieldset>

  <fieldset>
    <legend>Order Details</legend>
    <label><input type="radio" name="size" value="small"> Small</label>
    <br>
    <label><input type="radio" name="size" value="large"> Large</label>
  </fieldset>
</form>

Why bother? The two big wins

Visual win

It breaks a giant, scary form into smaller, manageable chunks. Instead of 20 fields in a row, the user sees “Section 1: Contact”, “Section 2: Order Details”, “Section 3: Payment”. Much less intimidating.

Accessibility win (the superpower)

Without it: “First Name, text field.” With it: “Entering ‘Shipping Address’ group. First Name, text field.” This gives crucial context about which “First Name” they’re filling out (shipping? billing? personal?).

Form validation: the bouncer

The club bouncerA bouncer checks you at the door before you get in: “No entry without an ID.” Form validation checks the data a user enters before the browser sends it to the server.

Its job is to stop the user and say “hold on, this isn’t right”:

  • “You left the Name field blank.”
  • “You’re ordering 500 pizzas, but the maximum is 10.”
  • “This doesn’t look like an email address. You forgot the @.”

Why validate? Data, Experience, Security

1 · Data

Without checks, people type “none” as a phone number, “asdf” as an email, or leave the name blank. Validation keeps the information correct and complete.

2 · Experience

Without it: fill 20 boxes, click Submit, see “Error occurred”, no idea why. With it: “Please enter a valid email” right away, so mistakes are easy to fix and users complete the form smoothly and stay happy.

3 · Security

Attackers type dangerous code into form fields to damage a database or website. Checking input is part of the defence.

Checks done in the browser like this are called client-side validation: fast, easy, and instant feedback. They are just attributes on your inputs.

Client-side checks don’t protect the server Anyone can switch off HTML validation in DevTools or send data straight to the server without your form. Browser validation is for data quality and user experience; real security needs the server to validate everything again.

Validation attributes

AttributeRuleExample
requiredMust fill: the box can’t be empty.<input type="text" name="user" required>
maxlength / minlengthCharacter limits. With maxlength the browser simply stops accepting keystrokes.maxlength="2" for a state code like “KA”
min / maxNumber range; works on type="number", type="date" and similar.min="1" max="10"
patternCustom rule: the value must match a regular expression (regex).pattern="[0-9]{5}" = exactly 5 digits
readonlyVisible but uneditable. Still sent to the server.value="bobjones" readonly
disabledCompletely off: greyed out (faded), can’t be clicked or used, and not sent.value="1" disabled

required: the must-fill rule

<label for="username">Username:</label>
<input type="text" id="username" name="user" required>

Submit it empty and the browser shows a message like “Please fill out this field.”

maxlength: the character limit

Like a tiny box on a paper form that physically can’t fit more letters.

<label for="state">State code:</label>
<input type="text" id="state" name="state" maxlength="2">

The user can type only 2 letters, like “KA” or “MH”.

min and max: the number range

<label for="qty">Quantity (1-10 only):</label>
<input type="number" id="qty" name="quantity" min="1" max="10">

pattern: the custom rule

The bouncer says: “Your ID must be a 5-digit number, no letters.” Patterns use a mini-language called regex (regular expressions).

<label for="zip">Zip (5 digits):</label>
<input type="text" id="zip" name="zipcode" pattern="[0-9]{5}">
[0-9]{5}

[0-9] · any one digit from 0 to 9

{5} · exactly 5 of them: 12345 passes, 1234A fails

readonly vs disabled

<label for="user">Username:</label>
<input type="text" id="user" name="username" value="bobjones" readonly>
<label for="qty2">Quantity:</label>
<input type="number" id="qty2" name="quantity" value="1" disabled>

Key terms

Form (<form>)
An invisible wrapper around form controls that tells the browser where (action) and how (method) to send their data.
action
The form attribute holding the server address that receives the submitted data, like the “To:” on an envelope.
enctype
How form data is packed before sending; the default URL-encoded string for text, or multipart/form-data for file uploads.
Form control
An element the user fills in or clicks, such as <input>, <textarea>, <select> or <button>.
name attribute
The label attached to a field’s data when it is sent, as in MainCourse=Cheeseburger. Fields without a name are not sent.
value attribute
The data a field holds: default text for typed fields, or the hidden answer sent for a chosen radio, checkbox or option. On submit and reset buttons it is the button text.
id attribute
A unique name for one element on the page, used to link a label to its input and to target the element from CSS or JavaScript.
Radio button
A round input for choosing exactly one option; radios sharing the same name form one group.
Checkbox
A square input for choosing any number of options; each ticked box sends its value under the shared name.
Dropdown (<select>)
A collapsible list of <option> elements for choosing one item from many while saving space.
Label (<label>)
A text description linked to a form field through matching for and id; clicking it focuses the field and screen readers announce it.
Fieldset and legend
<fieldset> groups related fields inside a border; <legend> is the group’s title, announced by screen readers.
Client-side validation
Checks done by the browser before sending, using attributes like required, min and pattern. Helpful for users, but the server must validate again.
pattern
A validation attribute holding a regular expression the value must match, such as [0-9]{5} for exactly five digits.
readonly vs disabled
Both block editing; a readonly field’s value is still sent, a disabled field is greyed out and not sent.

Self-check

Pick an answer. You’ll see right away whether it’s correct and why.

Which <form> attribute says where the data should be sent?

  1. method
  2. target
  3. action
  4. enctype

action is the destination address; method is how it is sent, and target is where the reply opens.

A field has value="Lemonade" but no name. What does the server receive for it?

  1. Lemonade
  2. Nothing at all
  3. drink=Lemonade
  4. An error message

The browser only sends fields that have a name. Without one, the value is thrown away.

Three radio buttons let the user pick all three at once. What is most likely wrong?

  1. They have no id
  2. They have no checked
  3. They have no value
  4. They don’t share the same name

Radios become one “pick only one” group by sharing the exact same name.

Your form has <input type="file">. Which enctype do you need?

  1. multipart/form-data
  2. application/x-www-form-urlencoded
  3. text/plain
  4. None; files are sent automatically

The default encoding can’t carry files. multipart/form-data splits the form into parts, including the file.

In <option value="CAN">Canada</option>, what does the server receive if it is chosen?

  1. Canada
  2. option
  3. CAN, under the select’s name
  4. Both Canada and CAN

Users see the text between the tags; the server gets the option’s value, paired with the <select>’s name.

What links <label for="x"> to its input?

  1. The input’s name="x"
  2. The input’s id="x"
  3. The input’s value="x"
  4. Placing them on the same line

A label’s for must match the input’s id. Then clicking the label focuses the input.

You show a user’s account number in a form. They must not change it, but the server needs it. Which attribute?

  1. disabled
  2. required
  3. hidden text in a <p>
  4. readonly

readonly blocks editing but still sends the value. disabled would not send it at all.

Your form uses required and pattern. Is the server now safe from bad input?

  1. No; browser checks can be bypassed, so the server must validate too
  2. Yes, the browser blocks all bad data
  3. Yes, if the form uses POST
  4. Only if type="password" is used

Client-side validation helps users, but anyone can skip it. Security comes from checking again on the server.

Which value of pattern accepts exactly five digits?

  1. [5]{0-9}
  2. [0-5]
  3. [0-9]{5}
  4. {5}[digits]

[0-9] means one digit and {5} means exactly five of them.

All of it, in one sentence

A <form> wraps controls and sends them to its action; every field needs a name (and a value for choices) to be sent, a <label> linked by for/id to be usable, and validation attributes to catch mistakes early, while the server still checks everything again.
