Linux Terminal and Shell

Understand the difference between the terminal and the shell, read every part of the prompt, and know exactly what happens each time you press Enter.

How users interact with an operating system

The operating system (OS) is the main software that manages the computer’s hardware (CPU, memory, storage, keyboard, mouse, network and other devices) and provides services to applications. Users and apps don’t control that hardware directly; they go through an interface. There are two common kinds:

GUI · Graphical User Interface

How it works: you click icons, open windows and navigate menus with a mouse.

Why use it: intuitive and beginner-friendly. You explore visually without memorising anything.

CLI · Command-Line Interface

How it works: you type precise text commands into a terminal.

Why use it: much faster for complex tasks, precise, and easy to automate. Linux servers are built around CLI control to save resources.

Pointing at the menu vs ordering by nameAt a busy dhaba you can point at pictures on the menu card (GUI): easy, but slow if you want twelve things. Or you can say “two masala dosa, one filter coffee, no sugar” (CLI): you need to know the words, but once you do, it is fast, exact and repeatable.

Why the command line exists

A GUI is perfect for browsing the web, but it has hard limits when you manage systems. The CLI is the standard for system administrators, DevOps engineers and cloud work for four reasons:

Speed in repetition

Clicking through the same 20 menus every day is slow. A typed command is instantly repeatable.

Remote access

A server in another country has no screen you can see. Sending text over the internet is fast and reliable; streaming a remote desktop can be slow or impossible.

Saves resources

Drawing windows and icons eats memory and CPU. Many servers have no GUI at all, so all the power goes to websites and databases.

Automation

Put commands in a text file (a script) and let it run unattended while you sleep. Automating mouse clicks is extremely hard.

In the field (FDE) The customer’s GPU server, their Kubernetes pod, the VM behind their firewall: none of them will give you a desktop. You will get an SSH session and a prompt. Being calm and fluent at the CLI is a core FDE skill.

What is a terminal?

A terminal is a text-based interface where you enter commands and see the results. Open one and you see a prompt where you can type something like ls. The terminal takes your keyboard input and displays whatever the command prints. Its job is input and output:

Input

Receives what you type on the keyboard.

Output

Displays the results on screen.

Errors

Shows error messages when something goes wrong.

Cursor

Shows where the next character will appear.

Important The terminal does not understand commands. It is a screen and a keyboard. Understanding is the shell’s job (two sections down).

Types of Linux terminals

All of these let you work with text, but they work in different ways.

1 · GUI terminal (terminal emulator)

What: the ordinary terminal app on your desktop (GNOME Terminal, macOS Terminal, Konsole).

How: runs in a normal window; resize it, copy and paste, open tabs for different tasks.

Idea: the everyday way to use the CLI alongside your browser and other apps.

2 · Virtual console (TTY)

What: a pure-text, full-screen terminal built into Linux, separate from the desktop. TTY stands for teletypewriter, an old hardware term.

How: press Ctrl + Alt + F3 (F1–F6 on many systems) for a black screen with just text.

Idea: if the desktop freezes, switch to a TTY to fix things or reboot, no mouse needed.

3 · Pseudo-terminal (PTY)

What: a software-simulated terminal used behind the scenes.

How: a GUI terminal window or an SSH session has no physical keyboard wired to a screen, so software creates a PTY that makes the shell believe it is talking to a real terminal.

Idea: whenever an app simulates a terminal for a shell, it uses a PTY. No need for deeper details yet.

The shell: the program that understands you

The terminal gives you a place to type, but it has no idea what ls, cd or mkdir mean. The shell is the program that reads your command, interprets it and starts the right program.

A shell is a command interpreter, the bridge between you and the operating system. Its main job:

ReadInterpretRunDisplay
The counter and the cookAt a Swiggy cloud kitchen, the order screen (terminal) shows what came in and displays “ready”. It can’t cook. The cook (shell) reads the order, decides what it means and gets the right dishes made. Terminal = the screen; shell = the one who understands.

How a Linux command actually works

Knowing this journey makes everything later much less mysterious. Here is what happens when you type ls and press Enter:

  1. 1
    You enter a commandYou type ls and press Enter.
  2. 2
    The terminal receives the inputIt collects each character and passes the finished line to the shell running inside it.
  3. 3
    The shell reads the commandBash (our example shell) receives the text ls.
  4. 4
    The shell interprets itWhich command is it? Is it a built-in (handled inside Bash) or an external program on disk? Which options and arguments came with it?
  5. 5
    The shell starts the programls is external, so Bash asks the OS to create a new process and run that program.
  6. 6
    System callsTo do anything real (start a process, read a file, use memory) a program must ask the kernel through a system call, because ordinary programs may not perform privileged operations. You don’t write syscall code; just know every command relies on calls like “create a new process” or “open this file”. → shell → system call → kernel
  7. 7
    The kernel does the workOnly the kernel may control hardware and core resources, so it works with the file system, memory, devices and processes.
  8. 8
    The result comes backKernel → shell / process → terminal → you. The list of files appears on your screen.

Different Linux shells

Linux and UNIX have several shells. Each one reads your commands and runs them, but with different features and syntax.

1 · Bourne shell (sh)

By Stephen Bourne at AT&T Bell Labs, late 1970s. The grandfather of modern shells; it introduced core ideas all shells still use.

Experience: simple and lightweight, but old: no Up-arrow history, no advanced completion.

Why it matters: portability. sh exists on virtually every UNIX/Linux system, so scripts written for it run anywhere. (On Ubuntu, sh is actually dash, a small modern Bourne-compatible shell.)

2 · Bash (bash)

By Brian Fox for the GNU Project: the “Bourne Again SHell”, a compatible, feature-rich replacement for sh.

Key features: command history (↑/↓), Tab completion, aliases (short names for long commands), and powerful scripting with variables and control structures.

Why it matters: the industry standard and the default shell on most Linux distributions and servers.

3 · Korn shell (ksh)

By David Korn at Bell Labs, built to be great at both interactive use and advanced scripting.

Experience: big productivity and scripting improvements over earlier shells.

Why it matters: rarely pre-installed on desktop Linux, but a heavyweight in enterprise UNIX such as IBM AIX.

4 · C shell (csh)

By Bill Joy at the University of California, Berkeley, for programmers.

Experience: introduced interactive features like command history early on. Its syntax is modelled on the C language and differs from Bourne-style shells.

Why it matters: comfortable for developers who already wrote C.

5 · T shell (tcsh)

An enhanced C shell with the same C-like syntax.

Key features: command-line editing (fix typos before Enter), command history and auto-completion.

Why it matters: the go-to on many UNIX systems for people who liked C syntax but wanted a friendlier experience.

6 · Z shell (zsh)

A powerful modern shell for daily use and scripting.

Key features: excellent completion, advanced history, programmable visual prompts, and plugins and themes (e.g. Oh My Zsh).

Why it matters: loved by developers; the default login shell on modern macOS.

To try any of them (if installed), type its name and press Enter:

sh      # Bourne-compatible shell
bash    # Bourne Again Shell
ksh     # Korn shell
csh     # C shell
tcsh    # T shell
zsh     # Z shell

Bash: starting and identifying your shell

Bash (“Bourne Again SHell”) plays two roles at once:

Interactive command interpreter

The shell you type commands into directly.

Scripting language

Save a sequence of commands in a file and run them together as a script.

It is everywhere in professional work: Linux administration (users, files, services), automation of repetitive tasks, DevOps build and deployment scripts, server management, and reusable shell scripts.

Opening a terminal

When you launch a terminal (or log in over SSH), a shell session, usually Bash, starts automatically inside it.

Which shell is my default?

echo $SHELL
/bin/bash

$SHELL is an environment variable that usually holds your default login shell, a saved setting.

Which shell is running right now?

ps
    PID TTY          TIME CMD
   1234 pts/0    00:00:00 bash
   1250 pts/0    00:00:00 ps

ps shows the processes actually running in this terminal. The two can differ: if you start zsh by hand, $SHELL still says /bin/bash but ps shows zsh. Notice pts/0: that’s the pseudo-terminal your SSH session is using.

Starting and exiting nested shells

bash     # start a new Bash inside the current one: one level deeper
exit     # leave it (or press Ctrl+D) and return to the shell before

The command prompt, explained

Open a terminal on your EC2 server and you see a line like this, the command prompt. It isn’t decoration: it tells you who you are, where you are, and how much power you have before you run anything.

ubuntu@ip-172-31-8-5:~$

username: who is logged in.

hostname: which machine you’re on.

current directory: where you are (~ = home).

permission indicator: $ normal user, # root.

The general structure is username@hostname:current_directory$.

1 · Username → ubuntu

You are logged in with the user account ubuntu. Linux is multi-user: many users can exist on one system, each with their own files, permissions and settings, and everything you do is tied to your account. On AWS EC2 Ubuntu servers, ubuntu is the default user created at launch.

whoami
ubuntu

2 · Hostname → ip-172-31-8-5

The name of the computer you’re connected to. AWS builds it from the server’s private IP address 172.31.8.5: dots become dashes and ip- goes in front. It identifies the server inside the AWS network, which is very handy when you juggle several servers.

hostname
ip-172-31-8-5

3 · Current directory → ~

~ is the shortcut for your home directory, your personal working area. For ubuntu that’s /home/ubuntu.

pwd
/home/ubuntu

Move somewhere else and the prompt follows you:

cd /etc
ubuntu@ip-172-31-8-5:/etc$

4 · Permission indicator → $

$ means a normal user with limited permissions, which protects the system from accidental damage: you can’t change critical system files without special administrative privileges. Switch to the root user (for example with sudo -i) and the symbol becomes #:

sudo -i
root@ip-172-31-8-5:~#

Root has full control: it can change system files, install software, manage users and control the whole system.

See a #? Slow down. As root there is no safety net; one wrong rm can break the server. Type exit to return to your normal user as soon as the admin task is done.

This is a cloud server The ip-… hostname tells you you’re on an AWS EC2 instance in an AWS data centre, not your laptop. Such servers host websites, run applications, databases and backend services, and are great for learning administration. Every command you run affects that server.

Why it matters: commands act on files based on your location and permissions. Glancing at the prompt (identity, system, location, power level) before pressing Enter prevents a lot of mistakes.

Understanding command structure

Almost every Bash command has the same shape:

general form
command [options] [arguments]
ls -l /home

command: the program or built-in to run.

option (or flag): changes how the command behaves; -l = long listing.

argument: the thing the command acts on.

Two rules Put a space between each part. And Linux is case-sensitive: File.txt and file.txt are two different files, and LS is not ls.

Built-in vs external commands

Some commands live inside Bash itself and run instantly without starting a new program. Others are separate program files on disk that Bash launches as a new process.

Shell built-ins

Examples: cd, echo, pwd, export.

Handled inside Bash for speed, and because some (like cd) must change the shell’s own state, which only Bash can do. A separate program changing its directory wouldn’t move your shell.

External commands

Examples: ls, cat, cp, mv.

Separate executable files, typically in /bin or /usr/bin. Bash finds them and starts each as a new process.

Ask Bash how it will treat a name with type:

type cd
type cat
type ls
cd is a shell builtin
cat is /usr/bin/cat
ls is aliased to `ls --color=auto'

On Ubuntu, ls is an alias (that’s why folders show in colour). Underneath it is still the external program; type -P ls prints its file: /usr/bin/ls.

/bin or /usr/bin? On modern distributions, /bin is just a link to /usr/bin, so /bin/ls and /usr/bin/ls are the same file.

How Bash finds external commands: $PATH

When you type ls, Bash must know where that program lives. The answer is the environment variable PATH: a list of directories separated by colons (:). Bash searches them in order and runs the first match.

echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
lsBash searches PATHfinds the executableruns it

which and command -v

Both tell you what a PATH search would find:

which ls
command -v cat
/usr/bin/ls
/usr/bin/cat

command -v is built into the shell and also reports aliases and built-ins (try command -v ls and command -v cd); which only searches PATH.

In the field (FDE) “python: command not found” or “it runs the wrong Python” on a customer box is almost always a PATH problem. which python3 and echo $PATH are the first two commands to run.

The Bash environment and variables

The environment is the set of information (variables and settings) available to programs launched from the shell: your home directory, your username, where to look for commands, and so on.

Shell variables

Create your own variable, then read it back with a $:

name="John"
echo $name
John
No spaces around = name = "John" fails: Bash thinks name is a command. Write name="John". This is the most common beginner mistake.

Key terms

CLI
Command-Line Interface: working with a computer by typing text commands instead of clicking.
GUI
Graphical User Interface: working with a computer through windows, icons and menus with a mouse.
Terminal
A text interface that takes your keyboard input and displays output and errors; it does not interpret commands itself.
TTY (virtual console)
A full-screen text console built into Linux, reached with keys like Ctrl+Alt+F3, independent of the graphical desktop.
PTY (pseudo-terminal)
A software-simulated terminal that GUI terminal windows and SSH sessions use so the shell behaves as if it had a real terminal.
Shell
A command interpreter program that reads, interprets and runs your commands, then shows the result; the bridge between you and the OS.
Bash
The “Bourne Again SHell” from the GNU Project; the default shell on most Linux systems and a scripting language.
Command prompt
The line such as ubuntu@ip-172-31-8-5:~$ showing username, hostname, current directory and permission level.
Root user
The all-powerful administrator account; its prompt ends with # instead of $.
Option (flag)
A modifier such as -l that changes how a command behaves.
Argument
The thing a command acts on, such as a file or directory path.
Built-in command
A command executed inside the shell itself without starting a new program, such as cd or echo.
External command
A separate program file on disk, such as /usr/bin/ls, that the shell starts as a new process.
PATH
An environment variable listing colon-separated directories the shell searches, in order, to find external commands.
Environment variable
A named value (e.g. HOME, USER, PATH) passed to programs started from the shell; view them with env or printenv.

Self-check

Pick an answer. You’ll see right away whether it’s correct and why.

Which part actually understands what mkdir means?

  1. The terminal
  2. The keyboard driver
  3. The shell
  4. The monitor

The terminal only carries text in and out. The shell interprets the command and starts the right program.

Your desktop freezes. What lets you fix things without the GUI?

  1. Switching to a virtual console (TTY) with Ctrl+Alt+F3
  2. Opening another GUI terminal tab
  3. Starting zsh
  4. Running echo $SHELL

TTYs are text consoles built into Linux, independent of the graphical desktop.

Your prompt reads root@web-01:/var/log#. What is true?

  1. You are user web-01 in your home directory
  2. You are a normal user in /var/log
  3. You are root in your home directory
  4. You are root, on host web-01, in /var/log

username@hostname:directory, and # means root.

Why must cd be a shell built-in?

  1. It is too small to be a file
  2. It has to change the shell’s own current directory
  3. External programs can’t use the disk
  4. Built-ins are always newer

A separate process changing its own directory wouldn’t move your shell. Only Bash can change its own state.

You type myscript and get command not found, but the file exists in ~/tools. Most likely reason?

  1. The terminal is broken
  2. Bash is case-insensitive
  3. ~/tools is not in PATH
  4. You need a TTY

Bash only searches the directories listed in PATH for external commands.

In ls -l /home, what is /home?

  1. An argument
  2. An option
  3. The command
  4. An environment variable

The argument is the thing the command acts on; -l is the option.

Which line correctly creates a variable in Bash?

  1. name = "John"
  2. $name="John"
  3. set name "John"
  4. name="John"

No spaces around = and no $ when assigning; use $name only to read it.

echo $SHELL says /bin/bash, but ps shows zsh. Why?

  1. ps is wrong
  2. $SHELL is your default login shell; you started zsh by hand
  3. Bash and zsh are the same program
  4. The PATH is empty

$SHELL is a saved setting; ps shows what is really running now.

Which shell is the default on most Linux servers?

  1. csh
  2. ksh
  3. bash
  4. tcsh

Bash is the industry standard and default on most distributions; zsh is the default on modern macOS.

All of it, in one sentence

The terminal carries your text in and out, the shell (usually Bash) reads and interprets it, finds the program through PATH or runs a built-in, and asks the kernel to do the work, while the prompt constantly tells you who you are, where you are and how much power you have.
