API Basics

Learn how your Python program can ask another program for data over the internet, read the JSON answer, and stay calm when something goes wrong.

The problem: data that lives somewhere else

Until now your programs used data you typed yourself or saved in files. Many real apps need data that lives somewhere else: today’s weather, exchange rates, train timings, the price of a pizza.

Say you open a food delivery app and search “Pizza near me”. The app must show which restaurants are available, what pizzas they have, the prices, and whether each restaurant is open right now. All of that lives in the restaurant’s own system. The food app doesn’t have it. How does it get it?

Idea 1: type it ourselves

Menus and prices change every day and there are thousands of restaurants. We can’t retype all of it again and again.

Idea 2: open their database directly

No restaurant gives strangers full access. Their database may use a format we don’t understand. And one mistake from us could damage or delete their data.

We need a safe, fixed way to ask. The restaurant decides what we may ask and how; we follow those rules and get an answer. That fixed way of asking is called an API.

What is an API?

API stands for Application Programming Interface:

WordMeaningEasy way to remember
ApplicationA program: a weather app, a bank app, your own Python codethe programs that want to talk
ProgrammingIt is used by code, not by a person clicking buttonsprograms use it
InterfaceThe point where two things meet and talklike the buttons on a TV remote

An API is a way for one application to talk to another. It is a communication bridge that lets one program ask another program for data or work.

Because the rules are fixed, the two programs don’t need to know anything about each other’s insides. Your program can be in Python and the other in Java; they only need to follow the API rules. Most APIs today work over the internet; these are called web APIs.

Why we need APIs

Modern applications depend on many other systems. An online shop doesn’t build its own payment, delivery and email systems. It uses existing ones through their APIs.

Example: a customer clicks Pay Now. The website doesn’t process the card itself. It asks a payment service through an API and gets the result back.

No rebuilding

We reuse what already exists.

Systems stay private

Others can use only what the API allows.

Any language

Programs in different languages can work together.

When an application asks an API for something, that is an API request. It says what you want to do, which data you want, and any extra information needed. After processing, the API sends something back: the API response.

Client and server

“Our program” and “the other program” have proper names: client and server.

Client: the one who asks

The program that sends the request: a web browser asking for a page, a mobile app asking for the weather, your Python program asking for data. Client is a role, not a device. Whoever asks is the client.

Server: the one who answers

The program that receives the request and sends the response. It keeps the data (or knows where it is), runs all the time waiting for requests, and serves many clients at once. A server never starts the conversation.

The rules of the conversation

Client and server are usually on different computers, sometimes in different countries, connected through the internet.

  • the client always starts by sending a request,
  • the server replies with a response,
  • one request gets one response.

Where the API fits

The client doesn’t know how the server stores its data, and doesn’t need to. The API decides what requests the client may send, in what format the request must be written, and in what format the response comes back. In the restaurant, the menu and the waiter together are the API. The same API can serve a website, a mobile app and a Python program alike.

Good to know: one program can be both A food app’s own server is a server for your phone, but becomes a client when it asks a payment service to charge your card. The role depends on who asks and who answers at that moment.

HTTP: the shared language

Client and server need an agreed format: where a message starts, what is being asked, where the data is. An agreed set of communication rules is a protocol. Web APIs use HTTP, the HyperText Transfer Protocol.

  • Every API call is one HTTP request and one HTTP response.
  • Your browser uses HTTP every time you open a website.
  • HTTPS is the secure version: the S means messages are encrypted, so nobody in between can read them.
Our practice API All examples use JSONPlaceholder (jsonplaceholder.typicode.com), a free fake-data API with posts, to-dos and users. No sign-up needed, and nothing you send is really saved, so experiment freely.

GET and POST

A simple way to remember: GET = take data, POST = give data.

GET: read or fetch

GET reads data and does not change anything on the server. GET /posts/1 means “Please show me post number 1.” When you type an address in the browser and press Enter, the browser sends a GET.

Query parameters

To get only some of the data, add query parameters after a ?. Each is a key=value pair; several pairs are joined with &.

https://jsonplaceholder.typicode.com/posts?userId=1&id=3

? starts the query parameters

userId=1: key userId, value 1

& separates two parameters

id=3: a second key and value

This reads: “Give me posts where userId is 1 and id is 3.”

POST: send new data

POST sends new data to the server, usually to create something or submit a form: sign up, log in, add a comment, place an order. POST /posts means “Please add this new post.” The data goes in the request body, not in the URL:

POST request with a JSON body
POST /posts HTTP/1.1
Content-Type: application/json

{
  "title": "Hello",
  "body": "My first post",
  "userId": 1
}

The Content-Type header tells the server the body is JSON. A successful POST usually gets 201 Created.

Why POST uses a body URLs are visible, have length limits, and are saved in browser history and server logs. Passwords and large data must never go in a URL. (The body is hidden from the address bar, but it is only protected from eavesdroppers when you use HTTPS.)

Making API requests

With a browser (GET only)

Your browser is already an HTTP client. Open this address in a new tab:

https://jsonplaceholder.typicode.com/posts/1

The browser sends a GET and shows the JSON response:

{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit",
  "body": "quia et suscipit\nsuscipit recusandae consequuntur expedita et cum\n..."
}

Try a query parameter too: https://jsonplaceholder.typicode.com/posts?userId=1. A browser is great for quick GETs, but it can’t easily send POST data and can’t use the answer inside a program. For that, use Python.

With Python: the requests library

Python acts as the client using the requests library. Install it once (inside your virtual environment), then import it:

pip install requests

Sending a GET

import requests

response = requests.get("https://jsonplaceholder.typicode.com/posts/1")

print(response.status_code)   # 200
print(response.text)          # the content as text

requests.get(url) sends the request and returns a response object, kept here in response.

Passing query parameters

Instead of writing ?userId=1 by hand, pass a dictionary as params:

import requests

url = "https://jsonplaceholder.typicode.com/posts"
params = {"userId": 1}

response = requests.get(url, params=params)

print(response.url)
https://jsonplaceholder.typicode.com/posts?userId=1

requests builds the query string for you and safely encodes special characters. More parameters work the same way: params={"userId": 1, "id": 3} becomes ?userId=1&id=3.

Sending a POST

import requests

url = "https://jsonplaceholder.typicode.com/posts"

new_post = {
    "title": "Learning APIs",
    "body": "APIs are useful.",
    "userId": 1
}

response = requests.post(url, json=new_post)

print(response.status_code)   # 201 means created
print(response.json())
201
{'title': 'Learning APIs', 'body': 'APIs are useful.', 'userId': 1, 'id': 101}

Working with JSON

Ask an API for a student and it may answer:

{
  "id": 101,
  "name": "Rahul",
  "course": "Python"
}

This is JSON, JavaScript Object Notation. It began in the JavaScript world, but today almost every language reads it: Python, JavaScript, Java, C#, Go, PHP. It is easy for people to read and easy for programs to process. If you can read JSON, you can read almost any API answer.

Python app⇄ JSON ⇄JavaScript app

Objects: key-value pairs

A JSON object uses curly braces { } and stores key-value pairs. The key says what the value means. Keys are always in double quotes.

  "age": 22,
  "isStudent": true
}

Arrays: lists of values

A JSON array is a list of values in square brackets, like a Python list: ["Python", "JavaScript", "Java"]. APIs often send many records as an array of objects:

[
  { "id": 1, "name": "Rahul" },
  { "id": 2, "name": "Priya" },
  { "id": 3, "name": "Amit" }
]

Object { }

Holds key-value pairs. One thing with properties. Becomes a Python dict.

Array [ ]

Holds a list of values. A collection of things. Becomes a Python list.

Parsing and accessing

Parsing means turning JSON text into Python data. You already know the tool, response.json():

import requests

response = requests.get("https://jsonplaceholder.typicode.com/users/1")
data = response.json()          # JSON object → dict

print(data["name"])             # Leanne Graham
print(data["username"])         # Bret

A parsed array is a list, so use an index (starting at 0) or a loop:

users = requests.get("https://jsonplaceholder.typicode.com/users").json()   # JSON array → list

print(users[0]["name"])     # first user

for user in users:
    print(user["name"])     # every user

Real APIs put objects inside other objects. Here address is an object inside the student:

print(data["name"])                # Rahul

data["address"] gives the inner dictionary {"city": ..., "state": ...}; then ["city"] picks the city from it.

So far we saw the happy path. In real life the server may be down, the URL may be wrong, the internet may drop, or the API may send unexpected data.

Checking by hand

Don’t call response.json() straight away. Check first:

import requests

response = requests.get("https://jsonplaceholder.typicode.com/posts/1")

if response.status_code == 200:
    print("Success")
    print(response.json())
elif response.status_code == 404:
    print("Resource not found")
else:
    print("Something went wrong")

The better way: raise_for_status()

Let requests do the checking. raise_for_status() raises an HTTPError for any 4xx or 5xx status and does nothing for success:

response = requests.get("https://jsonplaceholder.typicode.com/posts/99999")

response.raise_for_status()   # raises HTTPError for 404

data = response.json()        # never reached
requests.exceptions.HTTPError: 404 Client Error: Not Found for url: https://jsonplaceholder.typicode.com/posts/99999

You catch that exception with Python’s try and except, which is the next section.

Handling API errors with exceptions

Connection errors

Sometimes your computer can’t reach the server at all: no internet, server unreachable, wrong host name, network trouble. requests raises a ConnectionError:

import requests

try:
    response = requests.get("https://this-site-does-not-exist-123.com")
    response.raise_for_status()
    print(response.json())

except requests.exceptions.ConnectionError:
    print("Could not connect to the server.")
Could not connect to the server.

A clear message instead of a crash with a confusing traceback.

Timeouts

Sometimes the server is reachable but too slow. Without a limit, your program may wait forever. Set a timeout in seconds:

import requests

try:
    response = requests.get("https://jsonplaceholder.typicode.com/posts", timeout=5)
    response.raise_for_status()
    print(response.json())

except requests.exceptions.Timeout:
    print("The server took too long to respond.")
Always set a timeout By default, requests sets no timeout, so a stuck server can hang your program indefinitely.

Invalid JSON

You expect { "name": "Rahul" } but the server sends plain text or an HTML page. Then response.json() fails:

import requests

try:
    response = requests.get("https://example.com")     # sends an HTML page, not JSON
    response.raise_for_status()
    data = response.json()
    print(data)

except requests.exceptions.JSONDecodeError:
    print("The server returned invalid JSON.")
The server returned invalid JSON.

(requests.exceptions.JSONDecodeError exists in requests 2.27 and newer.)

Several things can go wrong: one try, many excepts

import requests

try:
    response = requests.get("https://jsonplaceholder.typicode.com/posts/1", timeout=5)
    response.raise_for_status()
    data = response.json()
    print(data["title"])

except requests.exceptions.Timeout:
    print("Request timed out.")

except requests.exceptions.ConnectionError:
    print("Could not connect to the server.")

except requests.exceptions.HTTPError:
    print("The API returned an HTTP error.")

except requests.exceptions.JSONDecodeError:
    print("The server returned invalid JSON.")
Why Timeout comes first A timeout while connecting (ConnectTimeout) counts as both a Timeout and a ConnectionError. Python uses the first matching except, so listing Timeout first gives the right message.

A simple catch-all

RequestException is the parent of all the requests errors above, so one block catches them all:

try:
    response = requests.get("https://jsonplaceholder.typicode.com/posts/1", timeout=5)
    response.raise_for_status()
    data = response.json()
    print("Data received successfully.")

except requests.exceptions.RequestException as error:
    print("API request failed:", error)

Later, switch to specific exceptions when you want a different message for each problem.

A pattern to reuse

safe API call template
import requests

try:
    # 1. Send the request, with a timeout
    response = requests.get("https://jsonplaceholder.typicode.com/posts/1", timeout=5)

    # 2. Check the HTTP status
    response.raise_for_status()

    # 3. Parse the JSON
    data = response.json()

    # 4. Use the data
    print("Success:", data["title"])

except requests.exceptions.Timeout:
    print("Request timed out.")

except requests.exceptions.ConnectionError:
    print("Could not connect to the server.")

except requests.exceptions.HTTPError:
    print("API returned an error.")

except requests.exceptions.JSONDecodeError:
    print("Invalid JSON received.")

In the field (FDE) Customer systems (CRMs, ticketing tools, internal APIs) are slow, flaky and badly documented far more often than JSONPlaceholder. Timeouts, status checks and clear error messages are what keep your integration from silently hanging at 2 a.m.

Key terms

API
Application Programming Interface: a fixed set of rules that lets one program ask another program for data or work.
Web API
An API that is used over the internet, usually through HTTP.
Client
The program that starts the conversation by sending a request, such as a browser, a mobile app or a Python script. It is a role, not a device.
Server
The program that waits for requests, does the work and sends back a response, often to many clients at once.
HTTP / HTTPS
HyperText Transfer Protocol, the rules web clients and servers use to exchange requests and responses; HTTPS is the encrypted version.
Endpoint
One specific API address (method + path, like GET /posts/1) that does one specific job.
HTTP method
The verb in a request that says what to do: GET reads, POST creates, PUT replaces, PATCH partly updates, DELETE removes.
Headers
Name: value lines that carry information about a request or response, such as Content-Type or Authorization.
Request body
The data a client sends with a request, typically JSON in a POST; GET requests usually have none.
Query parameters
key=value pairs added to a URL after ? and joined with &, used to filter or shape a GET request.
Status code
A three-digit number in the response that says how it went: 2xx success, 3xx redirect, 4xx client error, 5xx server error.
JSON
JavaScript Object Notation, a text format of objects (key-value pairs) and arrays that almost every language can read; Python turns it into dicts and lists.
Parsing
Turning JSON text into Python objects, done with response.json().
raise_for_status()
A requests method that raises HTTPError if the response status is 4xx or 5xx.
Timeout
The maximum number of seconds to wait for a server; requests sets none by default, so you should always pass one.

Self-check

Pick an answer. You’ll see right away whether it’s correct and why.

In the restaurant analogy, what plays the role of the API?

  1. The customer
  2. The waiter
  3. The kitchen
  4. The food

The waiter carries your order (request) to the kitchen (server) and brings the food (response) back. You never enter the kitchen.

A food app’s backend asks a payment service to charge a card. In that moment, the backend is…

  1. Only a server
  2. Neither a client nor a server
  3. The database
  4. A client

Client is a role: whoever sends the request. The same program is a server for your phone and a client for the payment service.

Which method should you use to create a new record and send its data in the body?

  1. POST
  2. GET
  3. DELETE
  4. PATCH

POST sends new data in the request body to create something. GET only reads.

In /posts?userId=1&id=3, what does & do?

  1. Starts the query string
  2. Marks the end of the path
  3. Separates two query parameters
  4. Means “or”

? starts the query string and & joins one key=value pair to the next.

What is the difference between response.text and response.json()?

  1. They are identical
  2. .text is a string; .json() parses it into a dict or list
  3. .json() returns the headers
  4. .text only works for POST

Only the parsed result lets you write data["id"]; the text is just one long string.

Given {"students": [{"name": "Rahul"}, {"name": "Priya"}]}, how do you get "Priya"?

  1. data["students"]["Priya"]
  2. data["name"][1]
  3. data["students"][1]["name"]
  4. data[1]["students"]

Key into the object ("students"), index into the array ([1]), then key into that object ("name").

A request returns 503. What kind of problem is it?

  1. Success
  2. Redirect
  3. Something wrong with your request
  4. Something wrong on the server

5xx codes are server errors; 4xx codes mean the request itself had a problem.

Why should you always pass timeout= to requests.get()?

  1. Without it, requests may wait forever for a slow server
  2. It makes the server respond faster
  3. It is required or the call fails
  4. It retries automatically

requests has no default timeout. A timeout makes it give up and raise Timeout so your program can recover.

What does response.raise_for_status() do on a 200 OK response?

  1. Raises HTTPError
  2. Nothing; the program continues
  3. Returns the JSON
  4. Retries the request

It only raises for 4xx and 5xx status codes. On success it quietly does nothing.

All of it, in one sentence

An API is the waiter between a client and a server: the client sends an HTTP request (GET to take, POST to give), the server answers with a status code and a JSON body, and your Python code uses requests to send it, .json() to read it, and timeouts and exceptions to survive when it fails.
