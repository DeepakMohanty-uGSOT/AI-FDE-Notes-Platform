Pydantic: Validating Data

Describe your data once as a class, and let Pydantic check every piece of data at the door, so the rest of your code can trust it.

The problem: Python does not check data types

The TTE on the trainOn an Indian train, the ticket checker (TTE) checks every passenger once, at the start. After that, nobody in the coach asks you for your ticket again. Without a TTE, every passenger would have to check every other passenger, all the time. Pydantic is the TTE for your data: it checks once, at the entrance, and everything after that can trust it.

Through this note we build one running example: a shipment-booking system for a logistics company called SwiftCargo.

The problemModelsField typesRequired / optionalEmailStr, AnyUrlField() rulesValidatorsComputed & nestedExport

Python lets a variable hold any type of value and never stops you from mixing types. That is fine for small scripts, but it causes real trouble once other people start calling your functions. Here is a function SwiftCargo might use to register a shipment:

def register_shipment(sender_name, packages_count):
    print(f"{sender_name} is shipping {packages_count} package(s)")

register_shipment("Rohan Mehta", "three")
Rohan Mehta is shipping three package(s)

Python runs this without complaint, even though "three" is text, not a number. If a later part of the program does maths with packages_count (say, adding up packages across many shipments), it crashes there, and it is hard to trace the problem back to here.

Type hints don't fix it

def register_shipment(sender_name: str, packages_count: int):
    print(f"{sender_name} is shipping {packages_count} package(s)")

register_shipment("Rohan Mehta", "three")
Rohan Mehta is shipping three package(s)

Same result. Type hints in plain Python are notes for humans and code editors. Python ignores them while running the code.

Manual checks work, but don't scale

def register_shipment(sender_name, packages_count):
    if not isinstance(sender_name, str) or not isinstance(packages_count, int):
        raise TypeError("Invalid data type")
    print(f"{sender_name} is shipping {packages_count} package(s)")

register_shipment("Rohan Mehta", "three")
TypeError: Invalid data type

This works, but every function that uses shipment data would need the same checks copied in, which makes the code messy and easy to break. And there is a second problem: packages_count could be -5. It is an int, but it makes no real-world sense.

Type checking

Is it the right kind of value? "three" is not an int.

Value validation

Does the value make sense? -5 is an int, but not a valid package count.

These are two separate problems, and Pydantic takes both off your hands.

What Pydantic actually does

Pydantic lets you describe your data once, as a class, and then automatically checks any data you give it against that description. If the data is wrong, it stops immediately with a clear error instead of letting bad data slip through silently.

Using Pydantic always follows the same three steps:

  1. 1
    DescribeWrite your data as a class, called a model.
  2. 2
    FeedPass real data into that class. This is where the checking happens.
  3. 3
    UsePass the checked, safe object anywhere in your code. → no more checks needed

Installing Pydantic

pip install pydantic                # first install
pip install --upgrade pydantic      # if you already have an old version
Always use version 2. Pydantic has two major versions. Version 2 is much faster (its core is written in Rust) and its method names differ from v1 (model_dump() instead of dict(), field_validator instead of validator). Every example here is Pydantic v2. Check yours with python -c "import pydantic; print(pydantic.VERSION)".

Building your first model

A Pydantic model is a normal Python class that inherits from BaseModel. Each field is a name with a type hint:

from pydantic import BaseModel

class ShipmentBooking(BaseModel):
    sender_name: str
    packages_count: int

That is the whole description: a booking must have a sender_name (text) and a packages_count (a whole number).

Create an object from real data

data = {"sender_name": "Rohan Mehta", "packages_count": 3}
shipment1 = ShipmentBooking(**data)     # ** unpacks the dict into keyword arguments
print(shipment1)
sender_name='Rohan Mehta' packages_count=3

Now send bad data:

bad_data = {"sender_name": "Rohan Mehta", "packages_count": "three"}
shipment2 = ShipmentBooking(**bad_data)
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
packages_count
  Input should be a valid integer, unable to parse string as an integer [type=int_parsing, input_value='three', input_type=str]

We wrote no checking code. Pydantic did it automatically, just from the type in the class.

Reading a ValidationError Line 1 says how many errors and which model. Then, for each error: the field name, a plain-English message, and in brackets the error type and the bad input. Real output also ends with a link to the Pydantic docs for that error type; we leave it out in these notes.

Use the checked object

def register_shipment(shipment: ShipmentBooking):
    print(f"Registered: {shipment.sender_name}, {shipment.packages_count} package(s)")

register_shipment(shipment1)
Registered: Rohan Mehta, 3 package(s)

register_shipment() checks nothing itself. It trusts shipment because Pydantic already validated it. An update_shipment() function could accept the same ShipmentBooking type, again with no repeated checking code.

Field types: numbers, flags, lists and dictionaries

A model can mix any Python types, such as str, int, float and bool. Pydantic checks each field against its own type.

class ShipmentBooking(BaseModel):
    sender_name: str
    packages_count: int
    package_weight_kg: float
    is_fragile: bool

data = {
    "sender_name": "Rohan Mehta",
    "packages_count": 3,
    "package_weight_kg": 12.5,
    "is_fragile": True
}
shipment1 = ShipmentBooking(**data)
print(shipment1)
sender_name='Rohan Mehta' packages_count=3 package_weight_kg=12.5 is_fragile=True

Lists and dictionaries: say what goes inside

Sometimes a field holds several values, like a list of handling instructions or key-value details about the package. If you write plain list or dict, Pydantic only checks the container, not what is inside it:

class ShipmentBooking(BaseModel):
    handling_notes: list      # only checks it's a list, not what's inside
    package_meta: dict        # only checks it's a dict, not what's inside

To check the items too, use List and Dict from the typing module and name the item types:

from typing import List, Dict
from pydantic import BaseModel

class ShipmentBooking(BaseModel):
    sender_name: str
    handling_notes: List[str]
    package_meta: Dict[str, str]

data = {
    "sender_name": "Rohan Mehta",
    "handling_notes": ["Keep upright", "Do not stack"],
    "package_meta": {"customs_code": "CN2201", "insurance_number": "INS7788"}
}
shipment1 = ShipmentBooking(**data)
print(shipment1)
sender_name='Rohan Mehta' handling_notes=['Keep upright', 'Do not stack'] package_meta={'customs_code': 'CN2201', 'insurance_number': 'INS7788'}

List[str] means “a list where every item must be text”. Put a number inside and Pydantic rejects it, pointing at the exact position:

1 validation error for ShipmentBooking
handling_notes.1
  Input should be a valid string [type=string_type, input_value=5, input_type=int]

Plain list would have let ["Keep upright", 5] straight through.

Shorter spelling On Python 3.9 and newer you can also write the built-in names directly: list[str] and dict[str, str]. They mean exactly the same as List[str] and Dict[str, str].

Required fields, optional fields and defaults

Every field is required by default

Using the model from the previous section, leave out handling_notes:

data = {
    "sender_name": "Rohan Mehta",
    "package_meta": {"customs_code": "CN2201"}
}
shipment1 = ShipmentBooking(**data)
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
handling_notes
  Field required [type=missing, input_value={'sender_name': 'Rohan Me...ustoms_code': 'CN2201'}}, input_type=dict]

This guarantees that required information is always provided before the object exists.

Making a field optional

Use Optional from typing and give the field a default of None:

from typing import List, Dict, Optional

class ShipmentBooking(BaseModel):
    sender_name: str
    handling_notes: Optional[List[str]] = None
    package_meta: Dict[str, str]

data = {"sender_name": "Rohan Mehta", "package_meta": {"customs_code": "CN2201"}}
shipment1 = ShipmentBooking(**data)
print(shipment1.handling_notes)
None
Optional[...] alone is not enough. Optional[List[str]] only means “a list of strings or None”. Without = None, the field is still required (you would have to pass None explicitly). The default is what makes it optional. List[str] | None = None is the newer spelling of the same thing.

A normal default value

class ShipmentBooking(BaseModel):
    sender_name: str
    is_fragile: bool = False

shipment1 = ShipmentBooking(sender_name="Rohan Mehta")
print(shipment1.is_fragile)
False

is_fragile was not provided, so Pydantic used the default False.

Ready-made validators: EmailStr and AnyUrl

Some formats show up so often that Pydantic ships special types for them, so you never write that checking logic (or a regular expression) yourself.

Email addresses with EmailStr

One extra install EmailStr uses a separate package, email-validator. Install it with pip install "pydantic[email]", or the import fails with an ImportError asking you to install it.
from pydantic import BaseModel, EmailStr

class ShipmentBooking(BaseModel):
    sender_name: str
    sender_email: EmailStr

shipment1 = ShipmentBooking(sender_name="Rohan Mehta", sender_email="rohan@cargolink.com")
print(shipment1)
sender_name='Rohan Mehta' sender_email='rohan@cargolink.com'
shipment2 = ShipmentBooking(sender_name="Rohan Mehta", sender_email="rohan-cargolink.com")
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
sender_email
  value is not a valid email address: An email address must have an @-sign. [type=value_error, input_value='rohan-cargolink.com', input_type=str]

Web addresses with AnyUrl

from pydantic import BaseModel, AnyUrl

class ShipmentBooking(BaseModel):
    courier_partner_url: AnyUrl

shipment1 = ShipmentBooking(courier_partner_url="https://cargolink.com/swift-express")
print(shipment1)
courier_partner_url=AnyUrl('https://cargolink.com/swift-express')

The value is now a URL object, not a plain string (older 2.x releases print it as Url('…')). A string without a scheme is rejected:

shipment2 = ShipmentBooking(courier_partner_url="cargolink.com")
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
courier_partner_url
  Input should be a valid URL, relative URL without a base [type=url_parsing, input_value='cargolink.com', input_type=str]
Need only web links? AnyUrl accepts any scheme (ftp://, postgres://…). Pydantic also has HttpUrl, which accepts only http and https.

Your own rules with Field()

EmailStr and AnyUrl cover common formats, but your business has its own rules, such as “a package weight must be greater than 0”. For these, Pydantic gives you the Field() function.

from pydantic import BaseModel, Field

class ShipmentBooking(BaseModel):
    package_weight_kg: float = Field(gt=0)      # gt = greater than

ShipmentBooking(package_weight_kg=5.5)          # valid
shipment1 = ShipmentBooking(package_weight_kg=-4.5)
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
package_weight_kg
  Input should be greater than 0 [type=greater_than, input_value=-4.5, input_type=float]

Combining constraints into a range

A delivery priority level must be between 1 and 5:

class ShipmentBooking(BaseModel):
    delivery_priority_level: int = Field(gt=0, le=5)   # value > 0 AND value <= 5

shipment1 = ShipmentBooking(delivery_priority_level=6)
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
delivery_priority_level
  Input should be less than or equal to 5 [type=less_than_equal, input_value=6, input_type=int]

Field() with text and lists

from typing import List, Optional

class ShipmentBooking(BaseModel):
    sender_name: str = Field(max_length=50)
    handling_notes: Optional[List[str]] = Field(default=None, max_length=5)
  • max_length=50 on a string: at most 50 characters.
  • max_length=5 on a list: at most 5 items.
  • default=None: Field() can carry the default and the rules together.

(There is also min_length for the other end.) Break both rules at once and Pydantic reports every problem, not just the first:

2 validation errors for ShipmentBooking
sender_name
  String should have at most 50 characters [type=string_too_long, ...]
handling_notes
  List should have at most 5 items after validation, not 6 [type=too_long, ...]

Adding notes to a field (metadata)

Field() can also attach a title, description and examples. These do not validate anything; they document the field, which matters most in APIs where they show up in the generated docs. The modern style puts Field() inside Annotated:

from typing import Annotated
from pydantic import BaseModel, Field

class ShipmentBooking(BaseModel):
    sender_name: Annotated[
        str,
        Field(
            max_length=50,                                   # validation
            title="Sender Name",                             # documentation only
            description="Full name of the person sending the package",
            examples=["Rohan Mehta", "Ananya Iyer"]
        )
    ]
In the field (FDE) When you wrap a customer’s system in an API, description and examples are what their developers read in /docs. A one-line description on each field saves you a dozen “what does this field mean?” emails.

When Pydantic auto-converts data (and how to stop it)

If Pydantic can safely turn a value into the expected type, it does. This is called type coercion:

class ShipmentBooking(BaseModel):
    package_weight_kg: float = Field(gt=0)

shipment1 = ShipmentBooking(package_weight_kg="25.5")
print(shipment1.package_weight_kg, type(shipment1.package_weight_kg))
25.5 <class 'float'>

The string "25.5" became the float 25.5. (This is why "3" is accepted for an int field, while "three" is not.) To accept only a real number, add strict=True:

class ShipmentBooking(BaseModel):
    package_weight_kg: Annotated[float, Field(gt=0, strict=True)]

shipment1 = ShipmentBooking(package_weight_kg="25.5")
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
package_weight_kg
  Input should be a valid number [type=float_type, input_value='25.5', input_type=str]

Field validators: your own custom rule

Field() handles built-in limits. For a business rule, such as “only emails from registered partner companies”, write a @field_validator:

from pydantic import BaseModel, EmailStr, field_validator

class ShipmentBooking(BaseModel):
    sender_email: EmailStr

    @field_validator("sender_email")
    @classmethod
    def check_partner_domain(cls, value):
        allowed_domains = ["swiftpartners.com", "cargolink.com"]
        domain = value.split("@")[-1]
        if domain not in allowed_domains:
            raise ValueError("email must belong to a registered partner domain")
        return value

Names its field

@field_validator("sender_email"), with @classmethod right below it.

Returns if valid

Receives the value and returns it (the returned value is what gets stored).

Raises if invalid

raise ValueError("…"). Pydantic turns it into a ValidationError.

print(ShipmentBooking(sender_email="rohan@cargolink.com"))
shipment2 = ShipmentBooking(sender_email="rohan@gmail.com")
sender_email='rohan@cargolink.com'
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
sender_email
  Value error, email must belong to a registered partner domain [type=value_error, input_value='rohan@gmail.com', input_type=str]

A field validator can also change the value

Because the returned value is what gets stored, a validator can transform data, for example store every sender name in uppercase:

class ShipmentBooking(BaseModel):
    sender_name: str

    @field_validator("sender_name")
    @classmethod
    def to_uppercase(cls, value):
        return value.upper()

shipment1 = ShipmentBooking(sender_name="Rohan Mehta")
print(shipment1.sender_name)
ROHAN MEHTA

Before or after: when does the validator run?

  • mode="before" runs before type conversion and receives the original value, exactly as sent.
  • mode="after" runs after conversion and receives the typed value. This is the default.

Watch what happens with a before-validator when the client sends "3" as text:

class ShipmentBooking(BaseModel):
    delivery_priority_level: int

    @field_validator("delivery_priority_level", mode="before")
    @classmethod
    def check_range(cls, value):
        if 0 < value < 6:
            return value
        raise ValueError("must be between 1 and 5")

shipment1 = ShipmentBooking(delivery_priority_level="3")
Traceback (most recent call last):
  ...
  File "main.py", line 7, in check_range
    if 0 < value < 6:
TypeError: '<' not supported between instances of 'int' and 'str'

The validator received the string "3", and Python cannot compare a number with a string. Notice that this is a raw TypeError that crashes the program, not a neat ValidationError: Pydantic only converts ValueError (and AssertionError) raised in a validator into a ValidationError. Switch to mode="after" and it works:

class ShipmentBooking(BaseModel):
    delivery_priority_level: int

    @field_validator("delivery_priority_level", mode="after")
    @classmethod
    def check_range(cls, value):
        if 0 < value < 6:
            return value
        raise ValueError("must be between 1 and 5")

shipment1 = ShipmentBooking(delivery_priority_level="3")
print(shipment1.delivery_priority_level)
3

Pydantic first converted "3" into 3, then the validator checked it.

When is before useful? For cleaning raw input before the type check, e.g. stripping spaces or turning "1,200" into "1200". Just remember the value can be of any type at that point.

Model validators: checking two fields together

A field validator only ever sees one field. Some rules need more. SwiftCargo requires an insurance number for any package worth more than ₹50,000. That depends on package_value and package_meta together, so we need a model validator:

from typing import Dict
from pydantic import BaseModel, model_validator

class ShipmentBooking(BaseModel):
    package_value: float
    package_meta: Dict[str, str]

    @model_validator(mode="after")
    def check_insurance(self):
        if self.package_value > 50000 and "insurance_number" not in self.package_meta:
            raise ValueError("packages over 50,000 must include an insurance_number")
        return self

A model validator does not name a field. In after mode it runs once all fields are validated and receives the whole object as self, so you read fields with dot notation (self.package_value). It must return the object.

shipment1 = ShipmentBooking(package_value=30000, package_meta={"customs_code": "CN2201"})
print(shipment1)

shipment2 = ShipmentBooking(package_value=75000, package_meta={"customs_code": "CN2201"})
package_value=30000.0 package_meta={'customs_code': 'CN2201'}
pydantic_core._pydantic_core.ValidationError: 1 validation error for ShipmentBooking
  Value error, packages over 50,000 must include an insurance_number [type=value_error, input_value={'package_value': 75000, ...ustoms_code': 'CN2201'}}, input_type=dict]

Note that 30000 was stored as 30000.0 (coerced to float), and that the error has no field name above it, because it belongs to the whole model.

Version note Older tutorials write an after-mode model validator as a @classmethod taking (cls, model). Since Pydantic 2.12 that style is deprecated and prints a warning; use an ordinary method with self, as above.
one field on its ownfield_validator
two or more fields togethermodel_validator

Computed fields: values Pydantic calculates for you

A computed field never comes from the user. Pydantic works it out from the other fields. A delivery vehicle’s fuel efficiency is a good example: nobody types it in, it is calculated from distance travelled and fuel used.

from pydantic import BaseModel, computed_field

class DeliveryTrip(BaseModel):
    distance_km: float
    fuel_used_liters: float

    @computed_field
    @property
    def fuel_efficiency(self) -> float:
        return round(self.distance_km / self.fuel_used_liters, 2)

trip1 = DeliveryTrip(distance_km=180, fuel_used_liters=15)
print(trip1.fuel_efficiency)
print(trip1.model_dump())
12.0
{'distance_km': 180.0, 'fuel_used_liters': 15.0, 'fuel_efficiency': 12.0}
  • Two decorators, in this order: @computed_field on top, @property right below.
  • -> float tells Pydantic the type of the result.
  • The method name is the field name: you read it as trip1.fuel_efficiency, with no brackets.
  • Unlike a plain @property, a computed field is included when you export the model with model_dump(), as the output shows.

Nested models: grouping related fields

Some fields are really a small group of fields. A delivery address is a city, a state and a pin code, not one long string. Build a separate model for it and use that model as a field type. This is a nested model.

from pydantic import BaseModel

class ShipmentAddress(BaseModel):
    city: str
    state: str
    pincode: str

class ShipmentBooking(BaseModel):
    sender_name: str
    delivery_address: ShipmentAddress

address1 = ShipmentAddress(city="Gurugram", state="Haryana", pincode="122001")
shipment1 = ShipmentBooking(sender_name="Rohan Mehta", delivery_address=address1)
print(shipment1)
print(shipment1.delivery_address.city)
print(shipment1.delivery_address.pincode)
sender_name='Rohan Mehta' delivery_address=ShipmentAddress(city='Gurugram', state='Haryana', pincode='122001')
Gurugram
122001

You can also pass the address as a plain dictionary; Pydantic builds the ShipmentAddress for you and validates it. If pincode is missing, the error path shows exactly where: delivery_address.pincode Field required.

Better organised

Related fields stay grouped instead of scattered.

Reusable

The same ShipmentAddress can sit inside a Customer or Employee model.

Easier to read

Anyone reading ShipmentBooking sees the address is its own structured thing.

Validated automatically

If delivery_address exists, every field inside it already passed its checks.

Turning a model into a dictionary or JSON

A validated object often has to go somewhere else: an API response, a log file, a database. Every model has two built-in export methods. Using shipment1 from the nested example:

to a Python dict
shipment_dict = shipment1.model_dump()
print(shipment_dict)
print(type(shipment_dict))
to a JSON string
shipment_json = shipment1.model_dump_json()
print(shipment_json)
{'sender_name': 'Rohan Mehta', 'delivery_address': {'city': 'Gurugram', 'state': 'Haryana', 'pincode': '122001'}}
<class 'dict'>
{"sender_name":"Rohan Mehta","delivery_address":{"city":"Gurugram","state":"Haryana","pincode":"122001"}}

Note the difference: the dict uses Python’s single quotes; the JSON string uses double quotes and no spaces, ready to send over the network.

Choosing exactly what gets exported

CallResult
model_dump(include={"sender_name"}){'sender_name': 'Rohan Mehta'}
model_dump(exclude={"sender_name"}){'delivery_address': {'city': 'Gurugram', 'state': 'Haryana', 'pincode': '122001'}}
model_dump(exclude={"delivery_address": {"state"}}){'sender_name': 'Rohan Mehta', 'delivery_address': {'city': 'Gurugram', 'pincode': '122001'}}

include keeps only the fields you name, exclude keeps everything except them, and a nested dict lets you exclude a field inside a nested model.

exclude_unset: leave out what was never given

class ShipmentBooking(BaseModel):
    sender_name: str
    is_fragile: bool = False

shipment1 = ShipmentBooking(sender_name="Rohan Mehta")
print(shipment1.model_dump(exclude_unset=True))
{'sender_name': 'Rohan Mehta'}

is_fragile was never passed in, so it is left out, even though the object still holds is_fragile = False. This is exactly what a PATCH-style update needs: “only the fields the client actually sent”.

In the field (FDE) Before writing customer data into logs, use exclude to drop sensitive fields (phone numbers, insurance numbers, tokens). One line keeps personal data out of places it should never be.

Common mistakes to avoid

MistakeWhy it’s a problem
Plain list / dict instead of List[str] / Dict[str, str]Pydantic checks only the container, not what is inside.
Optional[...] without a defaultThe field is still required. = None is what makes it optional.
Trusting type hints on normal functionsOnly fields inside a BaseModel are actually checked.
Forgetting return value in a field validatorThe function returns None, so the field silently becomes None.
Raising TypeError (or letting one happen) in a validatorOnly ValueError / AssertionError become a ValidationError; anything else crashes the program.
Using a field validator to compare two fieldsA field validator sees one field. Use model_validator.
Assuming Pydantic never converts data"25.5" becomes 25.5. Use strict=True when the exact type matters.
Reading a computed field by a different name, or with ()The method name is the field name, and it is a property: trip.fuel_efficiency.
Using EmailStr without email-validatorImport fails. Install pydantic[email].
About @classmethod Write @classmethod under @field_validator as the docs do. Pydantic quietly applies it for you if you forget, but the first parameter must still be cls (the class), not self, because no object exists yet while fields are being validated.

from typing import Annotated, Dict, List, Optional
from pydantic import BaseModel, EmailStr, Field, computed_field, field_validator, model_validator

class ShipmentAddress(BaseModel):
    city: str
    state: str
    pincode: str

class ShipmentBooking(BaseModel):
    sender_name: Annotated[str, Field(max_length=50)]
    sender_email: EmailStr
    package_weight_kg: float = Field(gt=0)
    package_value: float = Field(gt=0)
    shipping_cost: float = Field(ge=0)
    is_fragile: bool = False
    handling_notes: Optional[List[str]] = Field(default=None, max_length=5)
    package_meta: Dict[str, str]
    delivery_address: ShipmentAddress

    @field_validator("sender_name")
    @classmethod
    def to_uppercase(cls, value):
        return value.upper()

    @field_validator("sender_email")
    @classmethod
    def check_partner_domain(cls, value):
        if value.split("@")[-1] not in ["swiftpartners.com", "cargolink.com"]:
            raise ValueError("email must belong to a registered partner domain")
        return value

    @model_validator(mode="after")
    def check_insurance(self):
        if self.package_value > 50000 and "insurance_number" not in self.package_meta:
            raise ValueError("packages over 50,000 must include an insurance_number")
        return self

    @computed_field
    @property
    def cost_per_kg(self) -> float:
        return round(self.shipping_cost / self.package_weight_kg, 2)

Key terms

Pydantic
A Python library that checks data against a class-based description and raises a clear error when the data is wrong.
Model (BaseModel)
A class that inherits from Pydantic’s BaseModel; its type-hinted attributes are the fields that every input is validated against.
ValidationError
The exception Pydantic raises when input does not fit a model; it lists every failing field, a message and the error type.
Required field
A model field with no default value; leaving it out raises a “Field required” error.
Optional field
A field typed as Optional[X] (or X | None) and given a default such as = None, so it may be left out.
Field()
A Pydantic function that adds constraints (gt, le, max_length, strict), a default, or documentation metadata to a field.
Type coercion
Pydantic automatically converting a value to the declared type when it safely can, such as the string "25.5" to the float 25.5; strict=True turns it off.
field_validator
A decorator for a custom rule on one field; the method returns the (possibly changed) value or raises ValueError.
model_validator
A decorator for a rule that looks at several fields together; in after mode it receives the whole validated object.
computed_field
A property whose value Pydantic calculates from other fields and includes when the model is exported.
Nested model
A Pydantic model used as the type of a field in another model, so a group of related fields is validated as one structured unit.
model_dump() / model_dump_json()
Methods that export a model as a Python dictionary or a JSON string, with options like include, exclude and exclude_unset.

Self-check

Pick an answer. You’ll see right away whether it’s correct and why.

A plain function has packages_count: int in its signature. You call it with "three". What happens?

  1. Python raises a TypeError
  2. Python converts it to 3
  3. It runs normally; the hint is ignored
  4. Python raises a ValidationError

Type hints on ordinary functions are notes for humans and editors. Python does not enforce them at run time.

Which field is optional (can be left out)?

  1. notes: Optional[str]
  2. notes: Optional[str] = None
  3. notes: str
  4. notes: List[str]

A field is optional only when it has a default. Optional[str] without = None is still required.

A field is declared package_weight_kg: float = Field(gt=0). Which input passes?

  1. 0
  2. -4.5
  3. "heavy"
  4. "25.5"

Without strict=True, "25.5" is coerced to 25.5, which is greater than 0. Zero fails gt=0.

The rule is “if is_gift is True, gift_message must not be empty”. What should you use?

  1. model_validator
  2. field_validator("gift_message")
  3. Field(min_length=1)
  4. computed_field

The rule involves two fields at once, and only a model validator sees the whole object.

A mode="before" field validator on an int field receives "3" from the client. What type is value inside the validator?

  1. int
  2. float
  3. str
  4. It depends on the default

Before-validators run ahead of type conversion, so they see the raw input exactly as sent.

You forget to write return value at the end of a field validator. What is stored in the field?

  1. The original value
  2. None
  3. An empty string
  4. Pydantic raises an error

The validator’s return value is what gets stored. A function without return returns None.

A model has is_fragile: bool = False. You create it without is_fragile and call model_dump(exclude_unset=True). Is is_fragile in the result?

  1. Yes, as False
  2. Yes, as None
  3. Only if it’s a computed field
  4. No, because it was never set

exclude_unset drops fields that only have their default value because nobody passed them.

Which list field rejects ["Keep upright", 5]?

  1. List[str]
  2. list
  3. Optional[list] = None
  4. dict

List[str] checks every item. Plain list checks only that the container is a list.

All of it, in one sentence

Describe your data once with BaseModel, tighten it with Field() rules, add business logic with field_validator (one field) and model_validator (several fields), derive values with computed_field, group data with nested models, and export with model_dump(), so bad data is stopped at the door and everything after it can trust what it receives.
