Python Project Development

Go from one Python file to a tidy, shareable project: its own environment, a recorded list of packages, secrets kept out of the code, and type hints that say what each function expects.

From a script to a project

Home kitchen vs restaurant kitchenMaking Maggi for yourself needs one pan and no planning. A restaurant kitchen is different: separate stations, a written list of ingredients with exact brands, the safe locked away, and labels on every container so a new cook knows what is inside. A real Python project is the restaurant kitchen: organised, repeatable, and safe for other people to work in.

A script that solves one small problem can live in a single file. A real application quickly needs more:

An organised layout

Code, tests, docs and settings each have a clear home.

Isolated dependencies

Packages for this project don’t clash with other projects on the same machine.

Secrets out of the code

API keys and passwords come from the environment, not from the source file.

Type information

Other developers (and your editor) can see what a function expects and returns.

This note follows that order. Each idea comes with what it is, why it exists, and an example.

Project structure

Project structure is the overall organisation of an application: not just its source code, but also its tests, its list of dependencies and its documentation. In Python Fundamentals you used a package to organise the code itself. Project structure is the layer above that: it organises everything the project needs as a whole.

A basic layout

project folder
project/
├── app/                 → application code (a package)
│   ├── __init__.py
│   └── main.py
├── tests/               → test code
├── requirements.txt     → project dependencies
├── README.md            → project documentation
└── .gitignore           → files Git should ignore

All of the application’s own code sits inside the app package. Tests, requirements.txt, .gitignore and README.md sit beside it at the top level, because they support the project without being part of its logic.

Application code vs supporting files

Application code

The app/ folder: what the program actually does.

Supporting files

Tests, dependency list, docs and Git settings: what helps you build, run and share it.

This split makes it easy to see what the application does and which files support it.

What is .gitignore? A plain text file that tells Git which files or folders should not be tracked or uploaded, such as virtual environments, .env files, cache files (__pycache__/) and generated files.

Structure grows with the project

Small scriptMultiple modulesPackagesApplication structureProduction project

You don’t need a complex structure on day one. Start simple and organise the project as it grows.

The problem with installing packages globally

Different projects may need different versions of the same package:

Project Arequests==2.28
Project Brequests==2.32

If both projects use the same global Python, only one version can be installed at a time. Installing the version one project needs can break the other project. Global installation also makes it hard to:

  • reproduce the same environment on another machine, and
  • keep development and production environments consistent.

Virtual environments

Separate tiffin boxesIf the whole family packs lunch into one big box, the dal leaks into the rice. Give each person their own tiffin and nothing mixes. A virtual environment is a separate tiffin box of packages for each project.

A virtual environment is an isolated Python environment created for one specific project. It keeps that project’s installed packages separate from the system Python and from every other project.

Creating one with venv

venv is Python’s built-in module for this, so there is nothing extra to install. .venv is the most common folder name (venv is also common; any name works).

python -m venv .venv

This creates a .venv folder holding the project’s own Python and its own place for packages. It simply sits beside your code as another folder:

project/
├── .venv/               → the isolated Python environment
├── app/
│   ├── __init__.py
│   └── main.py
├── tests/
├── requirements.txt
├── README.md
└── .gitignore

Activating and deactivating

Creating the environment is not enough. You also activate it, which tells this terminal to use that environment’s Python and packages instead of the system ones, for the rest of the terminal session.

Operating systemActivate
Windows.venv\Scripts\activate
Linux / macOSsource .venv/bin/activate
Any (to leave)deactivate

After activating, the prompt usually shows the environment name in front, like (.venv).

Checking which Python is active

python --version
where python       # Windows
which python       # Linux/macOS

where / which prints the path of the Python being used. After activation, that path should point inside the .venv folder, not to the system installation.

C:\projects\project\.venv\Scripts\python.exe
C:\Python312\python.exe

(On Windows, where lists every match; the first line is the one that runs.)

Why .venv is not committed to Git

  • It can be recreated from requirements.txt at any time.
  • It makes the repository unnecessarily large.
  • It contains files specific to your operating system and machine.
.gitignore
.venv/

This line tells Git to ignore the entire .venv folder.

pip: installing external packages

pip is Python’s package installer. It installs third-party packages (libraries written by other developers, such as requests or pandas) that your project needs. With a virtual environment active, pip installs into that environment only.

TaskCommand
Install a packagepip install requests
Install a specific versionpip install requests==2.32.0
Upgrade a packagepip install --upgrade requests
Uninstall a packagepip uninstall requests
List installed packagespip list
Show package detailspip show requests

Once installed, a package is imported exactly like a built-in module, with the same import styles you learned in Python Fundamentals:

import requests

requirements.txt: recording dependencies

requirements.txt is a text file listing the packages a project needs and their versions, one per line:

requirements.txt
pandas==2.2.2
numpy==1.26.4

Generating and installing

After installing what you need inside the virtual environment, generate the file automatically:

pip freeze > requirements.txt

pip freeze lists every installed package with its exact version (including the helper packages they pulled in), and > saves that output into the file. Later, on another machine or in a fresh environment:

pip install -r requirements.txt

-r tells pip to read the package list from the file.

  1. 1
    Developerinstalls packages in the venv and runs pip freeze > requirements.txt.
  2. 2
    requirements.txtis committed to Git with the code.
  3. 3
    New environmenta teammate or a server creates a fresh venv.
  4. 4
    pip install -r requirements.txtinstalls everything on the list.
  5. 5
    Same dependencieseveryone runs the same package versions. → reproducible
In the field (FDE) “It works on my laptop but not on the customer’s server” is very often a version mismatch. A pinned requirements.txt is the first thing to check, and the first thing to ship.

Version constraints

requirements.txt doesn’t have to pin one exact version. It can also allow a range using a version constraint:

ConstraintMeaning
requests==2.32.0Exactly this version
requests>=2.30.0This version or newer
requests<=2.32.0This version or older
requests>=2.30,<3.0Any version in this range

Constraints exist so that an unrelated upgrade can’t silently break your project.

Exact pin ==

Most stable and predictable: the same version every time. But someone must edit the file to get a newer version.

Range >=, <=, both

Picks up minor updates automatically, at some risk that an update changes behaviour unexpectedly.

Environment variables

Applications need values such as API keys, passwords, database URLs and port numbers. Writing them straight into the code is unsafe:

API_KEY = "my-secret-key"   # anyone who can read the code can see this
The bank lockerYou don’t write your locker PIN on the cheque book you hand to everyone. You keep it separately and bring it only when needed. An environment variable keeps a value outside the source code and hands it to the program only when it runs.

Setting one in the terminal

ShellCommand
Windows Command Promptset API_KEY=abc123
Windows PowerShell$env:API_KEY="abc123"
Linux / macOSexport API_KEY=abc123

A variable set like this lives only in that terminal session. Close the terminal and you must set it again.

Reading it in Python

app.py
import os

api_key = os.getenv("API_KEY")
print(api_key)

Run it in the same terminal where you set the variable:

python app.py
abc123

os.getenv("API_KEY") looks for a variable named API_KEY and returns its value, or None if it isn’t set. You can give a default that is used when it is missing:

port = os.getenv("PORT", "8000")

Secrets stay out of the code, and development and production can use different values without changing the code.

.env files for local configuration

Setting variables by hand in every new terminal gets tiring. A .env file keeps your local environment variables in one place, in the project’s root folder:

.env
API_KEY=abc123
DATABASE_URL=postgresql://localhost/mydb
DEBUG=True

Loading it with python-dotenv

Python does not read .env files by itself. The python-dotenv package loads them into the environment:

pip install python-dotenv
app.py
from dotenv import load_dotenv
import os

load_dotenv()                     # copy values from .env into the environment

api_key = os.getenv("API_KEY")    # read them exactly as before
print(api_key)
abc123

load_dotenv() loads the values; os.getenv() reads them, just like in the previous section. The only difference is where the values come from.

Everything is a string Environment variable values are always read as strings. os.getenv("DEBUG") returns the string "True", not the boolean True. Convert it yourself, e.g. debug = os.getenv("DEBUG") == "True".

.env and Git

A .env file may hold secrets, so it must not be committed:

.gitignore
.venv/
.env
Important .env is a convenience for local development, not a secure secret manager. Production applications should use the deployment platform’s secret-management system.

Project configuration

Configuration means values that control how an application behaves without changing its main logic, such as DEBUG, PORT, DATABASE_URL and LOG_LEVEL.

Instead of calling os.getenv() all over the project, keep configuration in one place, such as a configuration module:

app/config.py (a simple example)
import os
from dotenv import load_dotenv

load_dotenv()

DEBUG = os.getenv("DEBUG", "False") == "True"
PORT = int(os.getenv("PORT", "8000"))
DATABASE_URL = os.getenv("DATABASE_URL")
LOG_LEVEL = os.getenv("LOG_LEVEL", "INFO")

Elsewhere you just write from app.config import DEBUG. The same setting can have different values in different environments:

DevelopmentDEBUG=True
ProductionDEBUG=False

So the same application code runs in every environment without edits.

In the field (FDE) Every customer has a different database URL, API keys and log level. Keeping all of that in environment variables read by one config module means you deploy the same code everywhere and only change the settings.

Type hints

Without type information, it isn’t clear what a function expects:

def calculate(a, b):
    ...

Are a and b numbers, strings, something else? Type hints are optional annotations that describe the expected types of variables, parameters and return values. They make code easier to understand and help editors and type checkers catch mistakes.

On variables

name: str = "Deepak"
age: int = 20
price: float = 99.5
is_active: bool = True

On functions

def calculate(a: int, b: int) -> int:

a: int, b: int → each parameter is expected to be an integer

-> int → the function is expected to return an integer

def calculate(a: int, b: int) -> int:
    return a + b

Type hints are not enforced

age: int = "twenty"   # still runs!
Python won’t stop you Python does not check type hints at runtime. They act as documentation and as input for editors and type-checking tools (like mypy), which warn you before you run the code.

Hints for collections

You can describe both the collection and what it contains:

CollectionExampleMeaning
Listnames: list[str] = ["Rahul", "Amit", "Priya"]a list of strings
Dictionarymarks: dict[str, int] = {"Python": 90, "SQL": 85}string keys, integer values
Tuplecoordinates: tuple[int, int] = (10, 20)exactly two integers
Setunique_ids: set[int] = {1, 2, 3}a set of integers
def calculate_total(numbers: list[int]) -> int:
    return sum(numbers)

numbers: list[int] means the function expects a list of integers; -> int means it returns an integer.

Version note Writing list[str] and dict[str, int] with the built-in names works from Python 3.9. Older code uses List and Dict from the typing module.

Optional, Union and Any

Sometimes a value can have more than one possible type. A username may be None before it is provided and a string after.

Optional: a type or None

username: str | None = None          # modern syntax (Python 3.10+)

from typing import Optional
username: Optional[str] = None       # older syntax, same meaning

Both mean str or None. The | reads as “or”.

Union: one of several types

user_id: int | str                   # modern syntax

from typing import Union
user_id: Union[int, str]             # older syntax
def get_user(id: int | str) -> str:
    return str(id)

id may be an int or a str; the function returns a str.

Any: the type is unknown

from typing import Any

value: Any = 10

Any tells type checkers to allow any type. It is useful for dynamic data whose type you don’t know in advance.

Don’t overuse Any Every Any switches type checking off for that value, so real mistakes slip through unnoticed.

Type aliases

Complex hints get hard to read, especially when repeated:

users: dict[str, list[int]]   # string keys, lists of integers as values

A type alias gives that type a meaningful name:

UserScores = dict[str, list[int]]

scores: UserScores

Modern Python (3.12+) also has a dedicated type statement for aliases:

type UserScores = dict[str, list[int]]

Both create a name that stands for the same type, so you write UserScores instead of dict[str, list[int]] everywhere.

Key terms

Project structure
The overall organisation of an application’s files: application code, tests, dependency list, documentation and configuration.
.gitignore
A text file listing files and folders Git should not track, such as .venv/, .env and cache files.
Virtual environment
An isolated Python environment for one project, keeping its installed packages separate from the system Python and other projects.
venv
Python’s built-in module for creating virtual environments, used as python -m venv .venv.
pip
Python’s package installer, used to install, upgrade, list and remove third-party packages.
requirements.txt
A text file listing a project’s packages and versions, created with pip freeze > requirements.txt and installed with pip install -r requirements.txt.
Version constraint
A rule such as ==, >= or <= in a requirement that limits which package versions may be installed.
Environment variable
A named value supplied by the operating environment rather than the source code, read in Python with os.getenv().
.env file
A local file of KEY=value lines that python-dotenv loads into the environment; it must not be committed to Git.
Configuration
Values that change how an application behaves (debug mode, port, database URL) without changing its logic, ideally kept in one module.
Type hint
An optional annotation describing the expected type of a variable, parameter or return value; Python does not enforce it at runtime.
Optional / Union
Hints for values that may have more than one type: str | None (Optional) or int | str (Union).
Any
A special type from typing that tells type checkers to accept any type for a value.
Type alias
A name given to a complex type, such as UserScores = dict[str, list[int]], to make hints easier to read.

Self-check

Pick an answer. You’ll see right away whether it’s correct and why.

Project A needs requests==2.28 and Project B needs requests==2.32 on the same laptop. What is the cleanest fix?

  1. Install both versions globally
  2. Always use the newest version
  3. Give each project its own virtual environment
  4. Copy the requests source code into each project

A virtual environment per project keeps each project’s packages isolated, so different versions never conflict.

Why should .venv/ be listed in .gitignore?

  1. It can be recreated from requirements.txt and is large and machine-specific
  2. Git cannot store Python files
  3. It contains your passwords
  4. Activating it fails if Git tracks it

The environment is rebuilt with pip install -r requirements.txt; committing it only adds size and OS-specific files.

A teammate cloned your project. Which command installs exactly the packages you used?

  1. pip freeze > requirements.txt
  2. pip list
  3. python -m venv requirements.txt
  4. pip install -r requirements.txt

-r reads the package list from the file. pip freeze > is what creates the file.

What does the constraint requests>=2.30,<3.0 allow?

  1. Only version 2.30
  2. Any version from 2.30 up to, but not including, 3.0
  3. Any version below 2.30
  4. Version 3.0 and above

The two conditions combine: at least 2.30 and less than 3.0.

Your .env has DEBUG=False. What does bool(os.getenv("DEBUG")) give?

  1. False, because the value is False
  2. None
  3. True, because "False" is a non-empty string
  4. An error

Environment values are always strings. Any non-empty string is truthy, so compare the text instead, e.g. == "True".

What happens when you run age: int = "twenty"?

  1. Python raises a TypeError
  2. It runs; Python does not enforce type hints at runtime
  3. Python converts "twenty" to 20
  4. The line is ignored

Hints are documentation for people and tools. Only a type checker or editor would flag this.

Which hint means “a string, or nothing yet”?

  1. str & None
  2. list[str]
  3. Any
  4. str | None

str | None (or Optional[str]) means the value may be a string or None.

Why keep settings in one config.py module instead of calling os.getenv() everywhere?

  1. There is one place to see and change every setting
  2. os.getenv() only works inside config.py
  3. It makes the code run faster
  4. It encrypts the secrets

Central configuration is easier to understand and maintain; it does not secure or speed anything up on its own.

All of it, in one sentence

A real Python project has a clear structure, its own virtual environment, a pinned requirements.txt, secrets and settings in environment variables gathered in one config module, and type hints that tell everyone what each function expects.
