Intro to OOP · Part 1

See why “just write functions” stops working for big programs, then build your first classes and objects and understand exactly what self is.

Programming paradigms

Same dinner, different kitchensTwo cooks can make the same biryani. One follows a long numbered recipe card, step by step. The other sets up stations (rice, masala, garnish), each with its own ingredients and its own job. Same dish, different way of organising the work. A programming paradigm is a style of organising a program, not a language.

A programming paradigm is a method or style of writing programs. It describes how a programmer thinks about a problem and how the solution is structured in code: how the logic, the data and the flow of execution are organised. In one line, a paradigm answers:

“How should a program be written and organised?”

Why paradigms are needed

Early programs were small; one person could write and manage the whole thing. Today, programs have thousands or millions of lines, and that size brings problems:

Hard to understand

Nobody can hold the whole program in their head.

Ripple effects

A change in one part breaks another part.

Hard to reuse

Code is tied to one program and can’t be lifted out.

Slow to maintain

Fixing and updating software takes more and more time.

Each paradigm gives a structured way to organise programs so they are easier to write, understand and maintain. This lecture covers three:

ParadigmOrganises the program around…
Procedural (function-oriented)functions, or procedures, called in order
Object-oriented (OOP)objects that bundle data and behaviour
Modularseparate modules (files) that each handle one area

Procedural (function-oriented) programming

Procedural programming is one of the oldest paradigms. The program is split into functions; each does one task, and the program runs by calling them in a particular order. The focus is on steps, not on data: the logic decides how data flows from one function to the next.

marks.py · a function-based program
def read_marks():
    return [70, 80, 90]

def calculate_total(marks):
    return sum(marks)

def display_result(total):
    print("Total Marks:", total)

marks = read_marks()
total = calculate_total(marks)
display_result(total)
Total Marks: 240
read_marks()calculate_total(marks)display_result(total)Total Marks: 240

Notice: the program is divided into functions, each does one job, data is passed between them, and the functions control the flow. Data and behaviour are not grouped together.

Real-world version: a shop’s billing program

def read_prices():
    return [120, 45, 300]

def calculate_bill(prices):
    return sum(prices)

def print_bill(bill_total):
    print("Bill Total:", bill_total)

prices = read_prices()
bill_total = calculate_bill(prices)
print_bill(bill_total)
Bill Total: 465

This style works well for small programs. As programs grow, managing many functions and the data they share becomes difficult.

Where procedural programming struggles

1 · Large programs are hard to manage

A big program has many functions, and it becomes hard to see which function does what. When something breaks, finding where is difficult. Like a notebook with 200 steps on different pages: if one step is wrong, finding it is confusing.

2 · No proper data security

Data is open: any function can change it. Nothing restricts who can read or modify important values. Like keeping your phone unlocked all the time: anyone can change your contacts.

marks = 80

def change_marks():
    global marks
    marks = 0   # changed without permission

change_marks()
print(marks)
0

Real-world version: a bank balance stored as a global, so any function can wipe it out.

account_balance = 25000

def apply_charges():
    global account_balance
    account_balance = 0  # balance wiped out without permission

3 · Data can be modified by any function

Because data is shared, any function can change it at any time, and you can’t tell who changed it or why. If five people can write on the same paper, you won’t know who erased your answer.

score = 50

def update1():
    global score
    score = 70

def update2():
    global score
    score = 30

The final value of score depends on which function ran last, so it is unpredictable and confusing.

4 · Poor real-world mapping

Real-world things are objects, but procedural code thinks only in steps. A student has a name, roll number and marks together; here they are three loose variables, not one unit.

name = "Rahul"
roll_no = 12
marks = 85

def print_details():
    print(name, roll_no, marks)

5 · Code reusability problems

Functions that depend on shared global data only work inside that one program. Like a charger that works in one house and nowhere else.

total = 0

def add(value):
    global total
    total += value

add() needs a global called total to exist, so you can’t copy it into another program on its own.

6 · Maintenance and debugging are hard

Many functions are connected to the same data, so changing one can silently break another. Fixing one wire in a tangled cable disturbs the others.

7 · Not suitable for large-scale applications

Procedural style works for small programs but struggles with big systems, which need better structure, control and safety. Running a small shop is easy; running a mall needs proper systems and rules.

What is Object-Oriented Programming?

Object-Oriented Programming (OOP) is a way of writing programs that focuses on organising the program properly instead of writing one long list of steps. You first understand the real-life problem, then shape the program to match it. For now it’s enough to know OOP is a method of program design, not a set of syntax rules.

It was introduced because earlier approaches worked for small programs but ran into the problems above as programs grew. OOP improves structure by:

  1. 1
    Keeping related things togetherInformation and the actions on it sit in one place.
  2. 2
    Reducing confusionLarge programs are split into understandable pieces.
  3. 3
    Making code easier to read and modifyYou know where to look for each thing.
  4. 4
    Limiting the impact of changesA change stays inside one part instead of rippling everywhere.
A paradigm, not a language OOP is a style. Python, Java, C++ and many other languages support it, but the idea of OOP is independent of any one language.

Class: the blueprint

The cake recipeA recipe tells you how to make a cake: what goes in and what to do. But you can’t eat the recipe. A class is the recipe: a definition of what objects will have and do, not a usable thing itself.

A class is a blueprint, plan, model or design that describes how objects should be created. It specifies:

Properties

What information each object will have, like a name or an age.

Behaviours

What each object can do, like talking or walking. In code these are methods.

Nature of a class

  • Logical existence: it is a description, a definition in your code, not a real entity.
  • Holds no object data: a class doesn’t store any particular student’s name or marks. That data lives in the objects.
  • Passive: it describes actions that its objects will perform later.
  • Blueprint for objects: the “physical reality” built from a class is called an object.
Precise note for Python You will often hear “a class takes no memory”. In Python that isn’t literally true: the class itself is an object in memory (it holds the method definitions). What it doesn’t hold is each object’s own data, such as Rahul’s name. That is the idea the phrase is trying to convey.

Define once, create many

A class is reusable: write the plan once, then create as many objects as you need.

Plan (class)Result (objects)
One building blueprintMany buildings
One TV designThousands of physical TVs
One Student classMany real students: Rahul, Priya, Amit…

Defining a class in Python

class Student:
    """This is a description of the Student class"""
    # Inside here, we would define properties and behaviours
    pass
class Student: """docstring""" pass

class — the keyword that tells Python you are creating a blueprint.

Student — the class name. By convention it starts with a Capital Letter.

The docstring — an optional description of the class.

pass — a placeholder that keeps the class body empty for now.

Object: the real thing

An object is the real, usable entity created from a class. The class says how to build something; the object is the thing actually built and used to do work. Creating an object is also called creating an instance.

Nature of an object

Physical existence

It really exists in the program while it runs.

Uses memory

It occupies space in memory to store its data.

Actual data

It holds real values, like “Rahul” and 101.

Performs actions

It carries out the methods defined in its class.

Without objects, a program can’t do anything meaningful with a class: the class is only instructions.

If the class (blueprint) is…An object (real entity) could be…
StudentA student named “Rahul” with roll no. 101
MobilePhoneYour iPhone, with its own serial number and battery level
BankAccountPriya’s account with a balance of ₹500
TelevisionThe LG TV in your living room with volume set to 20

Creating an object in Python

# Assuming we have a class named Student
class Student:
    pass

# Creating an object
s = Student()
print(s)
<__main__.Student object at 0x000002ABDC92C830>

Student() tells Python to read the blueprint and build a real object. s is the name we use to reach it. (The hex number is the object’s memory location; yours will differ.)

Three analogies

Building blueprint

The architect’s plan sets floors, rooms and windows (class). You can’t live in the paper; only the constructed building is real (object).

TV design

LG’s engineers create one model design (class). You can’t watch the design, but the factory makes thousands of TVs from it (objects).

Idol mold

The festival mold defines the shape (class). The mold isn’t the idol, but it produces many identical idols (objects).

Reference variables

TV and remoteYou don’t control the TV by touching its circuits; you use the remote. The TV is the object, the remote is the reference, and the hand holding the remote is the variable. A variable doesn’t hold the object; it holds a reference that points to the object.

When you create an object, Python doesn’t put the object “inside” the variable. The object lives in memory, and the variable stores a reference (think: address) to it. That variable is a reference variable: a name tag telling Python which object you mean.

House and address The house is the object. Its address is the reference. The paper with the address written on it is the reference variable. You carry the address, not the house.

How a reference variable is created

class Student:
    def __init__(self, name):
        self.name = name

s1 = Student("Kumar Deepak")
print(s1.name)
Kumar Deepak
  1. 1
    Student("Kumar Deepak")creates an object in memory.
  2. 2
    s1 = …s1 becomes the reference variable and stores the object’s reference.
  3. 3
    s1.namefollows the reference to the object; .name reads the data stored inside it.

So s1 is not the object itself; it points to it. Real-world version: reading a phone’s brand through its reference variable.

class MobilePhone:
    def __init__(self, brand):
        self.brand = brand

my_phone = MobilePhone("Samsung")
print(my_phone.brand)
Samsung

Shared references and reassignment

Many names, one object

More than one reference variable can point to the same object. The object is created only once; s2 = s1 just copies the reference.

class Student:
    def __init__(self, name):
        self.name = name

s1 = Student("Kumar Deepak")
s2 = s1

s2.name = "Ravi"
print(s1.name)
Ravi

Real-world version: a joint bank account. When mom withdraws money, dad sees the new balance.

class BankAccount:
    def __init__(self, balance):
        self.balance = balance

dad_access = BankAccount(10000)
mom_access = dad_access

mom_access.balance = 7000
print(dad_access.balance)
7000
In the field (FDE) This is behind a classic production bug: you pass a config or customer object into a helper, the helper “tweaks” it, and the change leaks back to every other part of the service holding the same reference. If a function should not change the caller’s object, make a copy first.

Zero, one or many references

An object may have one reference variable, several, or none. When no reference points to an object any more, nothing can reach it, so it becomes eligible for garbage collection: Python frees its memory.

Reassigning a reference variable

s1 = Student("Kumar Deepak")
s1 = Student("Ravi")

Real-world version: a cab app cancels the first cab and points the booking to a new one.

class Cab:
    def __init__(self, driver):
        self.driver = driver

current_cab = Cab("Ramesh")
current_cab = Cab("Suresh")  # first cab cancelled, new cab assigned
print(current_cab.driver)
Suresh

Remember

  • A reference variable stores a reference to the object, not the object’s data.
  • You reach an object’s data and methods through a reference.
  • Many reference variables can point to the same object.
  • A reference variable can be reassigned to a different object.

The self variable

“My” on a formA college form says “Write your name, your roll number”. The same form works for every student because “your” always means whoever is filling it in right now. self is “your” for a method: it always means the object the method is running for.

self is a reference variable that always points to the current object. When an object calls the constructor or an instance method, Python automatically passes that object’s reference as the first argument, and the method receives it in the parameter named self.

Why it’s needed

A class can have many objects, each with its own name, roll number and marks. When a method runs, Python must know whose data to use. self makes sure that:

  • each object works only with its own data,
  • data of one object never mixes with another’s,
  • the same method behaves differently for different objects.

Rules

Always first

The first parameter of __init__ and of every instance method is self.

Never passed by you

You never write a value for self. Python takes the object reference and passes it for you, on every call.

Inside the class only

self exists only in the class’s methods. Outside, you use the object’s reference variable.

s1.greet()Python rewritesStudent.greet(s1)self = s1

self inside the class, references outside

Creating instance variables with self

Inside the constructor, self.something = value creates an instance variable: a variable that belongs to the object being built.

class Student:
    def __init__(self, name, roll_no):
        self.name = name
        self.roll_no = roll_no

s1 = Student("Sunny", 101)

When s1 is created, an object appears in memory, self.name and self.roll_no become part of it, and the values "Sunny" and 101 are stored inside. Every new object gets its own separate set of instance variables.

Accessing them inside the class: self.variable

class Student:
    def __init__(self, name, roll_no):
        self.name = name
        self.roll_no = roll_no

    def show_details(self):
        print("Student Name:", self.name)
        print("Roll Number:", self.roll_no)

s1 = Student("Sunny", 101)
s1.show_details()
Student Name: Sunny
Roll Number: 101

Real-world version: a product on a shopping site displays its own name and price.

class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    def show_details(self):
        print("Product:", self.name)
        print("Price:", self.price)

p1 = Product("Headphones", 1499)
p1.show_details()
Product: Headphones
Price: 1499

Accessing them outside the class: reference.variable

class Student:
    def __init__(self, name, roll_no):

self always means the current object

Two objects can call the same method. The code is identical, but self points to a different object in each call, so the output differs.

class Student:
    def __init__(self, name):
        self.name = name

    def greet(self):
        print("Hello, my name is", self.name)

s1 = Student("Sunny")
s2 = Student("Ravi")

s1.greet()
s2.greet()
Hello, my name is Sunny
Hello, my name is Ravi

Real-world version: two bank customers call the same method and each sees only their own balance.

class Customer:
    def __init__(self, name, balance):
        self.name = name
        self.balance = balance

    def show_balance(self):
        print(self.name, "has a balance of", self.balance)

c1 = Customer("Arjun", 5000)
c2 = Customer("Meera", 12000)

c1.show_balance()
c2.show_balance()
Arjun has a balance of 5000
Meera has a balance of 12000

self is not a keyword

Technically any name works for the first parameter, because Python passes the object into whatever that first parameter is called. self is a convention that Python developers everywhere follow.

works, but don’t
class Person:
    def show(name):  # not 'self'
        print("Hello")

p = Person()
p.show()
standard convention
class Person:
    def show(self):
        print("Hello")

p = Person()
p.show()
Hello

Both print Hello. In the first, name silently receives the object, which is confusing to read. Always use self.

A common error: constructor arguments

If the constructor takes only self but you pass values while creating the object, Python raises a TypeError.

class Student:
    def __init__(self):
        self.name = "Kumar Deepak"
        self.roll_no = 101

s1 = Student("Sunny", 101)
TypeError: Student.__init__() takes 1 positional argument but 3 were given

Why “3 were given” when you passed two? Because Python also passes the new object as self: that’s self, "Sunny" and 101, but __init__ only accepts self.

Real-world version: a pizza order class that takes no values, while the app passes a size and a price.

class PizzaOrder:
    def __init__(self):
        self.size = "Medium"
        self.price = 299

order = PizzaOrder("Large", 499)  # TypeError: the constructor accepts only self
TypeError: PizzaOrder.__init__() takes 1 positional argument but 3 were given
Fix it Make the constructor accept what callers pass: def __init__(self, size, price): and store them with self.size = size, self.price = price.

Points to remember about self

  • It is a reference variable pointing to the current object, supplied automatically by Python.
  • It is used to create and access instance variables inside the class.
  • Outside the class, use the object’s reference variable instead.
  • It is not a keyword, but always use the name self.

Key terms

Programming paradigm
A style of writing and organising programs, such as procedural, object-oriented or modular. It is not a programming language.
Procedural programming
A paradigm that splits a program into functions called in order, with data passed between them or shared globally.
Object-Oriented Programming (OOP)
A paradigm that organises a program into objects, each keeping related data and the actions on that data together.
Class
A blueprint that defines the properties and behaviours its objects will have. It does not hold any individual object’s data.
Object (instance)
A real entity created from a class, such as Student("Rahul"). It lives in memory and holds its own data.
Reference variable
A variable that stores a reference to an object rather than the object itself. Several reference variables can point to the same object.
Instance variable
A variable that belongs to one object, created inside the class with self.name = value.
self
The first parameter of the constructor and of every instance method; Python fills it automatically with the object the method is running for.
Constructor (__init__)
The special method Python runs automatically when an object is created, used to set up the object’s instance variables.
Garbage collection
Python’s automatic freeing of memory for objects that no reference variable points to any more.

  2. A type of variable
  3. A style of organising and writing programs
  4. A compiler setting

A paradigm is a way of thinking about and structuring code. Many languages can follow the same paradigm.

Why do global variables cause trouble in large procedural programs?

  1. Any function can change them, so you can’t tell who changed the data or why
  2. They are slower than local variables
  3. Python doesn’t allow them
  4. They can only store numbers

Shared, unprotected data can be modified from anywhere, which makes bugs hard to track and functions hard to reuse.

class A: with def __init__(self): .... What happens on A(5)?

  1. 5 is ignored
  2. TypeError: takes 1 positional argument but 2 were given

  4. The object is created with no data

After s1 = Student("X") then s1 = Student("Y"), what happens to the “X” object if nothing else refers to it?

  2. It merges with “Y”
  3. It stays reachable through s1
  4. Python raises an error

Reassignment moves the name to the new object. An object with no references can’t be reached, so Python frees it.

  1. self.name
  2. Student.self.name
  3. name on its own
  4. s1.name, using the object’s reference variable

self only exists inside methods. Outside, you go through a reference variable.

All of it, in one sentence

Procedural code gets messy as it grows, so OOP bundles data and behaviour into objects built from a class blueprint; you reach each object through a reference variable, and inside its methods the object refers to itself as self.
