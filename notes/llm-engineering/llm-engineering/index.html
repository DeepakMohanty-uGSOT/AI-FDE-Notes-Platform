LLM Engineering

Understand what really happens between “you send a prompt” and “text comes back”, so you can build LLM features that are accurate, fast and affordable.

What is an LLM?

The very well-read assistantImagine an assistant who has read millions of books, articles and code files. You say: “Write an email to my manager asking for leave tomorrow.” A second later it replies: “Dear Sir, I would like to request leave tomorrow due to…” That assistant is a Large Language Model.

A Large Language Model (LLM) is an AI model trained on a huge amount of text so that it can understand and generate human language. You give it text, called a prompt, and it gives text back, called a response or completion.

Large

Trained on a very large amount of text: books, articles, web pages, documents, code and conversations.

Language

Works with human language (English, Hindi, Kannada…) and with programming languages such as Python, JavaScript, Java and C++.

Model

A system that learns patterns from data, instead of following rules a programmer wrote.

Put together: an LLM is a large AI model trained on huge amounts of text to learn the patterns of language and generate useful text.

promptLLMresponse (completion)

Well-known LLM families include GPT (OpenAI), Claude (Anthropic), Gemini (Google) and Llama (Meta).

Why do we need LLMs?

Traditional software needs very specific instructions. Here is a support bot built with plain rules:

rule_bot.py
message = input("How can we help? ")

if "refund" in message:
    print("Refund request")
elif "late" in message or "delay" in message:
    print("Delivery issue")
else:
    print("Unknown request")

This breaks very quickly:

Same meaning, different words

“money back” means refund, but the rule only looks for the word refund.

Typos and slang

“refnd plz” or “paisa wapas” are not matched.

Other languages

You would need a separate set of rules for every language.

Endless rules

Every new phrasing needs another elif. The code never ends.

Rules work for exact, structured data. Human language is not exact. LLMs understand meaning and intent, not just keywords, and one model can handle many tasks without new rules for each one.

In the field (FDE) Customers often arrive with a pile of brittle keyword rules (an if/elif ticket router, regex email parsers). Replacing them with one well-tested LLM classification prompt is one of the most common and fastest FDE wins.

The journey of a prompt

When you send a prompt to an LLM, the text goes through a fixed series of steps. Each step gets its own section below; here is the whole journey once.

  1. 1
    TokenizerThe text is broken into small pieces called tokens. → Tokens
  2. 2
    Token IDsEach token becomes a number, because models only work with numbers.
  3. 3
    EmbeddingsEach number becomes a list of values that represents its meaning. → Embeddings
  4. 4
    Transformer layersThe tokens “look at” each other to understand the context. → Transformers
  5. 5
    ProbabilitiesThe model gives a score to every possible next token.
  6. 6
    Pick one tokenOne token is chosen, added to the text, and the process repeats. → Inference

Training vs inference, and how text is generated

Studying vs the examA student spends years studying, then sits in the exam hall and writes answers. Nothing new is learned in the exam hall. Training is the studying; inference is writing the exam.

An LLM has two completely different phases in its life:

Training (learning)

The model reads massive amounts of text and practises one task again and again: predict the next token. Every time it is wrong, its internal numbers, called weights or parameters, are nudged slightly. After billions of these corrections the weights hold the patterns of language, facts and reasoning.

Inference (using)

The trained model is simply used: you send a prompt and it generates a response. The weights do not change. The model does not learn from your conversation.

Training usually happens in stages:

  1. 1
    Pre-trainingLearn language from huge amounts of text. The result can continue text, but is not yet a good assistant.
  2. 2
    Instruction tuningTrain on examples of instructions with good answers, so it learns to follow instructions.
  3. 3
    AlignmentFeedback from humans (and from AI) teaches it to be more helpful, honest and safe.
Key idea As LLM engineers we almost always work with inference. Training a large model from scratch costs millions of dollars and is done by a handful of companies.

One token at a time

An LLM does not write a whole answer at once. At each step it looks at all the text so far, calculates the probability of every possible next token, picks one, adds it to the input, and repeats. This loop is called autoregressive generation.

Why this one fact matters A 500-token answer means the model ran its prediction 500 times. That explains why longer answers take longer and cost more, and why a model can “talk itself” into a wrong answer one token at a time.

Tokens: how text becomes numbers

Cutting vegetablesYou can’t cook a whole pumpkin in one go, and you don’t dice it into individual fibres either. You cut it into sensible pieces. Tokens are the “sensible pieces” an LLM cuts text into.

Computers cannot do maths on letters; a model only understands numbers. So the text must become a sequence of numbers first. The question is how to cut the text into pieces before numbering them.

Cut into…Vocabulary sizeProblem
CharactersTiny (letters, digits, symbols)Sequences become very long, and single letters carry little meaning
Whole wordsEnormousCannot handle new words, names, typos or other languages it has never seen
Tokens (middle path)Fixed, typically tens of thousands to a few hundred thousandBalanced: common words stay whole, rare words split into known pieces, so any text can be written

A token is a small chunk of text the model treats as one unit: a whole word, part of a word, a single character, a word with its leading space, or a punctuation mark.

"Hello"        -> 1 token
" learning"    -> 1 token   (the space is part of the token)
"Tokenization" -> 2 tokens  ("Token" + "ization")
"!"            -> 1 token
≈ 4characters per token (English)
≈ 0.75words per token

Tokenization

Tokenization converts text into tokens and then into token IDs. It is done by a separate program, the tokenizer, which ships with every model.

How does the tokenizer decide where to cut? Most modern tokenizers use Byte Pair Encoding (BPE): start with single characters (or bytes) and keep merging the pairs that appear together most often in a huge amount of text, until the vocabulary reaches its target size.

  • Common words usually become one token.
  • Rare words, names and typos split into several smaller tokens.
  • A space is usually attached to the start of the next word (" learning", not "learning ").
  • Different model families use different tokenizers, so the same text can have different token counts.

Input tokens, output tokens, cost and limits

Every request involves two kinds of tokens:

Input tokens (prompt tokens)

Everything you send: instructions, the user’s question, conversation history, documents.

Output tokens (completion tokens)

Everything the model generates in its response.

Providers charge per token, usually quoted per 1 million tokens. Input and output are priced separately, and output tokens typically cost several times more than input tokens, because each one needs its own prediction.

Worked example: a support assistant

10,000 requests a day, each about 1,200 input tokens and 300 output tokens. Example prices (not real prices; always check the provider’s pricing page, since prices change often): input $2.50 and output $10.00 per 1,000,000 tokens.

Input cost per request  = 1,200 / 1,000,000 x $2.50  = $0.0030
Output cost per request =   300 / 1,000,000 x $10.00 = $0.0030
Total per request       = $0.0060

Per day   = $0.0060 x 10,000 requests = $60
Per month = $60 x 30 days             = $1,800
Notice Output was only 20% of the tokens but 50% of the cost. Asking for shorter answers is often the cheapest optimisation you can make.

Token limits

LimitWhat it caps
Context windowTotal tokens (input + output) the model can handle in one request (next section)

When a response is cut off by the output limit, the API tells you why: OpenAI’s API returns finish_reason = "length" and Anthropic’s returns stop_reason = "max_tokens". That answer is incomplete, so your code should check for it.

In the field (FDE) A classic production bug: a JSON answer silently truncated by the output limit, then a parser crash downstream. Always log the stop reason and the token usage of every call; it is the first thing you will look at when a customer says “the bot is broken”.

Context windows

The study deskYou can only work with the papers that fit on your desk right now. Anything in the cupboard doesn’t count until you put it on the desk. The context window is the model’s desk: everything it needs must fit on it at the same time.

Something surprising: an LLM has no memory between requests. Each request is processed completely fresh. So how do chat apps remember the conversation? The app re-sends the whole conversation with every new message. The model only knows what is inside the current request, its context. If information is not in the context, the model cannot use it.

The context window is the maximum number of tokens a model can process in one request. All of these share it:

  • System instructions: how the assistant should behave (“You are a polite support agent…”).
  • Conversation history: the earlier messages.
  • Documents or data: files, search results, product details you add.
  • The current question: the user’s latest message.
  • The answer: the generated tokens take space in the same window.

Window sizes vary a lot: from a few thousand tokens in older models to hundreds of thousands, and over a million in some modern ones. Always check the model’s documentation.

Input and output share the window

Context window = 8,000 tokens

Case 1: input = 1,500  ->  room for output = 8,000 - 1,500 = 6,500 tokens
Case 2: input = 7,600  ->  room for output = 8,000 - 7,600 =   400 tokens
        if the answer needs 1,000 tokens, it is cut off after 400

Why not just stuff everything in?

Hard limit

Anything beyond the window cannot be sent; the request fails.

Cost

Every context token is an input token you pay for, on every request.

Speed

All input must be processed before the first word of the answer, so long prompts mean a longer wait.

Quality

Models often pay less attention to information buried in the middle of a very long context: the “lost in the middle” problem.

Key idea A good LLM engineer sends the model the right information, not all the information.

Context window vs model memory

Beginners often mix up what the model knows with what it remembers. There are three different kinds of “memory”:

Weights (knowledge)

What the model learned in training. Fixed after training; does not change when you chat.

Context window (working memory)

What is on the desk for this request only. Gone when the request ends.

External memory (app storage)

A database or file your app keeps, and puts back into the context when needed.

When a chat app “remembers” your name next week, the model has not learned anything. The app saved your name and placed it back into the context window; the weights never changed.

Embeddings: numbers that carry meaning

Roll numbers vs a mapRoll number 12 and roll number 13 sit next to each other on the register, but the two students may have nothing in common. A map is different: two cities with close latitude and longitude really are close. A token ID is a name tag. An embedding is a description.

The tokenizer gives each token an ID, like 9247 for “cat”. But IDs are only labels: the IDs of “cat” and “car” can be neighbours while the words have nothing in common. The model needs numbers that describe meaning, so that “cat” and “dog” get similar numbers and “car” gets very different ones.

An embedding is a list of numbers (a vector) that represents the meaning of a token, like coordinates on a map of meaning:

"cat"  -> [0.82, 0.10, 0.75, 0.05, ...]
"dog"  -> [0.79, 0.14, 0.71, 0.08, ...]
"car"  -> [0.05, 0.91, 0.12, 0.88, ...]

Nobody chooses these numbers by hand, and no single number has a name like “animal-ness”. The model learns them during training.

Converting tokens into vectors

The conversion is just a lookup. The model has a big table with one row per token in its vocabulary; the token ID says which row to pick.

"cat"token ID 9247row 9247 of the table[0.82, 0.10, 0.75, …]

The rows start as random values and are adjusted during training so that tokens used in similar ways end up with similar rows. The embedding table is part of the model’s weights.

Meaning as a map

  • Animals sit together, fruits sit together, vehicles sit together.
  • The distance between two points tells how related the meanings are.
  • Directions can carry meaning too. A famous (rough) example from early embedding research: king − man + woman ≈ queen.

Embedding dimensions

The dimension is how many numbers are in the vector. Toy examples use 2 to 4; real models use hundreds or thousands.

Model (example)Used forDimensions

These are examples; always check the model’s documentation. More dimensions give more room to describe meaning (often better quality) but cost more memory, slower search and higher cost.

Same model, both sides Documents and questions must be embedded with the same embedding model. Vectors from two different models cannot be compared.

Semantic similarity

Because meanings are now numbers, we can measure how close two meanings are. The most common method is cosine similarity: it looks at the angle between two vectors. A small angle (a value near 1) means similar meaning.

Toy 2-number vectors:
cat = (0.90, 0.25)   dog = (0.85, 0.42)   car = (0.08, 0.97)

cat <-> dog  =  0.98   (very similar)
cat <-> car  =  0.35   (far apart)
dog <-> car  =  0.52   (far apart)

Semantic means “about meaning”, so semantic similarity is similarity in meaning, not spelling. “refund” and “money back” share no letters, but their embeddings are close.

Where embeddings are used

Semantic search

Find documents by meaning, not only exact words.

RAG

Find the best pieces of your documents and paste them into the context window.

Recommendations

“People who liked this also liked…” = find the nearest vectors.

Clustering

Group thousands of support tickets by topic.

Duplicate detection

Find questions that mean the same thing.

Cross-language search

A Hindi question can match an English document, if the embedding model knows both languages.

Two places you’ll meet embeddings (1) Inside every LLM, as the first step after tokenizing. (2) In separate embedding models built only to create vectors for search. Both turn text into vectors of meaning.

One problem remains: inside the LLM, a token like “bank” gets the same vector in every sentence. The Transformer fixes this using the words around it. First, a little history.

Before Transformers: ANNs and RNNs

What is an ANN?

An Artificial Neural Network (ANN) is a computer system that learns from examples instead of following rules written by a programmer. Show it many students and who passed or failed, and later it can guess whether a new student will pass.

  1. 1
    InputsThe data given to the network: hours studied, attendance, previous marks.
  2. 2
    WeightsHow strongly each input affects the decision. If hours studied matter a lot and attendance less, give them 0.8 and 0.2.
  3. 3
    BiasAn extra value added to the weighted sum (weighted inputs + bias) that helps the neuron shift its decision.
  4. 4
    Activation functionTurns the number (say 0.92) into a decision, like a gate asking “is this strong enough to say Pass?”. It is also what lets networks learn complex, non-linear patterns.
  5. 5
    OutputThe final result: Pass / Fail.

Press Play: the network looks at the examples again and again (each full round is an epoch), adjusts its weights a little after each round, and the test loss falls from 0.715 towards 0.000. It can now tell a pass student from a fail student.

Where ANNs fall short

No memory

Each input is looked at once and forgotten. In “I grew up in France, so I speak fluent ___”, it has no sense that “France” came earlier, so it can’t connect it to “French”.

No sense of order

Inputs are a bag of numbers. “The dog bit the man” and “The man bit the dog” use the same words with opposite meanings, and a plain ANN can’t tell them apart.

RNN: an ANN with memory

A Recurrent Neural Network (RNN) is built for data that comes in order: sentences, speech, stock prices. It reads one item at a time, updates a small memory called the hidden state, and passes it to the next step.

An RNN fixed the memory problem but created new ones:

  • Too slow: each step waits for the one before, so it can’t use the full parallel power of GPUs, and training on huge text takes very long.
  • It forgets: the whole memory is one small box rewritten at every step. By the 500th word, the first word is almost gone.
  • Far-apart words are hard to connect: the first and last words of a long sentence are many steps apart.

Transformers and attention

In 2017, researchers at Google published “Attention Is All You Need” and introduced the Transformer. The big idea: don’t read word by word; look at all the words at once, and let every word directly look at every other word.

ANNRNNTransformer
How it readsone input at a time, no orderone word at a time, in orderall words at once
Memorynonesmall and fadeslooks at every word directly
Speed on long textfast, but no contextslowfast (runs in parallel)
Used forsimple predictionsolder speech and translation systemsall modern LLMs

The Transformer as a tower

Don’t worry about the maths. Think of a tower of identical floors, called blocks or layers. Text goes in at the bottom, every floor improves the understanding, and the prediction comes out at the top.

  1. 1
    Tokenizer and token IDsText becomes numbers.
  2. 2
    Embeddings + positionNumbers become vectors of meaning, plus information about where each token sits. Because a Transformer reads all words together, without position it could not tell “dog bit man” from “man bit dog”.
  3. 3
    Transformer block × NEach block has self-attention (tokens share information with each other) and a feed-forward step (each token is processed further on its own). The block repeats many times.
  4. 4
    Output scoresA score for every token in the vocabulary, which becomes the next-token probabilities.

Follow the three tokens of “The cat sat”: they become 3 IDs, then 3 embedding vectors (+ position). Block 1 outputs 3 vectors with a little more context, block 2 more, … block N outputs 3 vectors rich with context. Every block takes in and gives out vectors of the same size. After the last block, the vector of the last token (“sat”) is used to score the next token, here " on".

Attention, conceptually

Read: “The animal didn’t cross the street because it was too tired.” What does “it” mean? You know at once: the animal. A model must work this out too. Attention lets a token look at the other tokens and decide how much each one matters for understanding it.

Think of a library:

Query

Your question: “what am I looking for?”

Key

The title on each book: “what do I contain?”

Value

The content inside the book: “the information I can give.”

The better a book’s key matches your query, the more you read from its value. Every token asks a query, and every token offers a key and a value.

Self-attention

Self-attention is attention where tokens look at the other tokens in the same text (and at themselves), all at the same time, in three steps:

Scorehow related is each pair?Softmaxturn scores into % (each row sums to 100%)Mixblend in information using those %

A Transformer runs this many times in parallel. Each copy is a head, and each head can notice something different: grammar, who did what, nearby words. Their results are combined; this is multi-head attention.

How tokens change after attention

“I sat on the river bank.”

Before attention: the generic “bank” vector. After: pulled towards water, shore, river.

“I deposited cash at the bank.”

Before attention: the same generic vector. After: pulled towards money, account, branch.

Key idea The embedding gives the dictionary meaning; attention adds the meaning in this sentence. Early blocks tend to pick up simple things (grammar, nearby words); later blocks tend to pick up deeper things (meaning, intent).

Encoder and decoder

PartWhat it doesGood for / examples
EncoderReads the whole text and builds a deep understanding. Each word can look both left and right.Search embeddings, classification (BERT-style models)
DecoderWrites text one token at a time. Each token can only look at tokens before it; a mask hides the future, like covering the answer sheet with your hand.Chat LLMs: GPT-style models, Llama, Mistral, Qwen
Encoder + decoderThe encoder understands the input; the decoder writes the output.Translation: T5, the original 2017 Transformer

Why must the decoder hide future tokens? Because during generation the future tokens don’t exist yet, so training must match that. When people say “LLM” today, they usually mean a decoder-only Transformer.

Why Transformers power LLMs

  • Fast training: all tokens are processed in parallel across many GPUs.
  • Context understanding: any token can connect directly to any other, however far apart.
  • They scale: more data, parameters and compute usually give a better model.
  • One design, many jobs: text, code, images and audio.
  • The foundation: GPT, Llama, Gemini, Claude and almost all other LLMs are built on the Transformer or close variants.

Inference: from prompt to answer

Inference means using the trained model to produce an output for a new input. The weights are fixed; nothing is learned. Every time you press Enter in a chat app, you run inference, and inference is where an LLM engineer balances quality, speed and cost.

  1. 1
    Build the promptYour app combines system instructions + chat history + the new question.
  2. 2
    Send an API requestTogether with settings such as maximum output length and temperature.
  3. 3
    Run the modelThe server tokenizes the prompt and runs the model on GPUs.
  4. 4
    GenerateThe model produces tokens one by one.
  5. 5
    ReturnThe text comes back as the response (completion), with token usage and a stop reason.
one inference call with the OpenAI Python SDK
from openai import OpenAI

client = OpenAI()   # reads the OPENAI_API_KEY environment variable

response = client.chat.completions.create(
    model="gpt-4o-mini",          # example name: model line-ups change often
    messages=[
        {"role": "system", "content": "You are a polite support agent. Answer in 2 sentences."},
        {"role": "user", "content": "Where is my order #1234?"},
    ],
    max_tokens=300,               # cap the output length (and cost)
    temperature=0.3,              # low randomness for support answers
)

print(response.choices[0].message.content)   # the answer text
print(response.choices[0].finish_reason)     # "stop" = finished, "length" = cut off
print(response.usage.prompt_tokens, response.usage.completion_tokens)

Other providers use the same idea with slightly different shapes (for example, Anthropic’s Messages API takes the system prompt as a separate system parameter and requires max_tokens). Check each SDK’s docs.

Two phases: prefill and decode

Phase 1 · Prefill (prompt processing)

All prompt tokens are processed together, in parallel. GPUs are very good at this. A longer prompt still means a longer wait before the first word.

Phase 2 · Decode (generation)

The answer is produced one token at a time, each needing a full pass through the model.

Next-token prediction

At each step the model produces a probability for every token in its vocabulary:

Prompt: "The weather today is"
  sunny     42%
  cloudy    24%
  hot       14%
  rainy     10%
  cold       6%
  banana     4%
  ... thousands of other tokens with tiny chances
Key idea The model doesn’t “decide” one answer; it gives probabilities. A separate rule, called decoding, picks one token.

It then loops: predict → pick → append → repeat ("The weather today is" → " sunny" → "." → <end>). Generation stops when:

  • the model produces a special end token;
  • it reaches the maximum output tokens you set (the answer is cut off);
  • it produces a stop sequence you defined, for example a line END.

Decoding rules

RuleHow it picksFeel
GreedyAlways the most likely tokenSafe and repeatable, can sound dull
Random samplingRandomly, weighted by the probabilitiesMore natural, occasionally picks a silly token
Top-kKeep only the k best tokens, then sampleCuts off the long tail
Top-p (nucleus)Keep the smallest group whose chances add up to p (e.g. 70%), then sampleAdapts to how confident the model is

With top-p = 0.70 above: sunny (42%) + cloudy (24%) = 66%, still under 70%, so add hot (14%) → 80%. The model samples only from sunny, cloudy, hot; “banana” can never be picked. Most APIs let you set temperature and top-p, and some also top-k. Usually change one of them, not all.

Temperature

Temperature controls how random the choice is. Low: the model nearly always picks the top token. High: lower-chance tokens get picked more often.

TemperatureUse for
Low (0 to 0.3)Facts, code, data extraction, classification
Medium (around 0.7)Everyday chat, emails, summaries
High (1.0 or more)Stories, brainstorming, many different ideas
Three warnings (1) Temperature 0 gives almost the same answer each time, but not always exactly the same on every provider. (2) A low temperature does not remove hallucinations. (3) The allowed range differs between providers, and some newer (especially reasoning) models don’t let you change it. Check the docs.

Latency, cost and streaming

Inference latency

Latency is how long the user waits. Two numbers matter:

Time To First Token (TTFT)

The wait before the first word appears. Depends on network time and prompt length (prefill).

Tokens per second

How fast the rest of the answer is produced. Depends on model size and hardware.

Total time = TTFT + (output tokens / tokens per second)
           = 0.5 s + (300 / 50) s
           = 0.5 s + 6.0 s  =  6.5 s

Ways to reduce latency:

  • Send a shorter prompt and ask for a shorter answer (or set a lower maximum output).
  • Use a smaller, faster model for easy tasks.
  • Use streaming so the user sees words early.
  • Use the provider’s prompt caching (a repeated prompt prefix is reused), and choose a server region close to your users.

Inference cost

From the token section: $0.0060 per request, $1,800 a month at 10,000 requests a day. When you run your own model, the cost is the GPUs instead.

What drives the costWhy
Model sizeBigger models cost more per token
Input tokensLong prompts, chat history and documents are paid on every request
Output tokensUsually several times pricier than input tokens
Number of requestsCost grows with users
“Thinking” tokensReasoning models write extra hidden steps, usually billed as output tokens

Ways to reduce cost: trim or summarise old chat history and remove unneeded text; cap the output length; use a small model for simple tasks and a big one only when needed; cache repeated prompt parts and use cheaper batch options for non-urgent jobs where offered.

In the field (FDE) Before a customer pilot, build a one-page cost sheet: requests/day × (input tokens × input price + output tokens × output price) × 30, using their real prompts. Then show the two or three levers (smaller model, shorter history, caching) and what each saves. It turns an “AI is expensive” worry into a decision.

Streaming responses

Without streaming, the user stares at a blank screen for the full 6.5 seconds. With streaming, the server sends each token as soon as it’s ready, like a person typing.

streaming with the OpenAI Python SDK
stream = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Explain tokens in 3 lines."}],
    stream=True,
)
for chunk in stream:
    piece = chunk.choices[0].delta.content
    if piece:
        print(piece, end="", flush=True)   # show every small piece immediately

Good

Feels much faster, the user can start reading, and can stop early to save tokens.

Careful

You can’t check the full answer before showing it, and app code gets a bit more complex. A JSON answer isn’t valid until the last piece arrives.

Key idea Streaming does not make the total time shorter. It makes the first words arrive sooner.

What LLMs are good at

The brilliant new internFast, flexible, has read everything, never tired, and will occasionally state something wrong with total confidence. A good LLM engineer knows both sides of the intern.

Text generation

Prompt : Write a 2-line email asking my manager for leave tomorrow.
Output : Dear Sir, I would like to request leave tomorrow due to a family
         function. I will complete my pending work today.

Summarization

Prompt : Summarise this 20-page report in 5 bullet points.
Output : 5 short bullet points with the key findings

Question answering

From training knowledge, or, much more reliably, from a document you provide:

Prompt : Using the policy below, how many days do I have to return an item?
         Policy: Items can be returned within 7 days of delivery.
Output : You have 7 days from the delivery date.

Classification

This replaces the brittle refund/delivery rules from the start of this note with one instruction:

Prompt : Classify the message as Refund, Delivery issue or Other.
         Message: paisa wapas chahiye
Output : Refund

Information extraction

Pull structured data out of messy text. Ask for JSON, and check it with code.

Text   : Rahul Sharma booked 2 tickets to Goa on 12 Nov and paid Rs 8,400.
Output : {"name": "Rahul Sharma", "tickets": 2, "destination": "Goa",
          "date": "12 Nov", "amount": 8400}

Code generation

The model writes, explains and fixes code. Always run and test what it gives you.

Prompt: “Write a Python function that checks if a number is prime.”
def is_prime(n):
    if n < 2:
        return False
    for i in range(2, int(n ** 0.5) + 1):
        if n % i == 0:
            return False
    return True

Reasoning

Prompt : A pen costs Rs 12. I buy 7 pens and pay with Rs 100.
         How much change do I get? Think step by step.
Output : 7 x 12 = 84.  100 - 84 = 16.  The change is Rs 16.

Asking it to “think step by step” often helps. Some models are reasoning models that spend extra tokens “thinking” before answering: more time and money, better on hard problems. It is still pattern-based, not human thinking. For exact maths, let the model use a calculator or write code.

Multimodal capabilities

A multimodal model accepts more than text, usually images and sometimes audio or video; output is often still text.

  • Read a receipt, form, chart or handwriting from a photo.
  • Describe an image or answer questions about it.
  • Transcribe speech or answer questions about audio, with models that support it.
In the field (FDE) Most first enterprise use cases are some mix of classify, extract, summarise over the customer’s documents: invoices, tickets, KYC forms, call transcripts. Multimodal models now let you skip a separate OCR step for many scanned documents, but test accuracy on the customer’s worst scans first.

Limitations, hallucinations and evaluation

Hallucinations

A hallucination is an answer that sounds confident and correct but is false or made up. It happens because the model predicts likely-sounding text; it doesn’t look facts up and doesn’t know when it is guessing. A fluent answer is not proof of a true answer.

Common examples: fake facts and numbers, invented book or paper titles and web links, functions or settings that don’t exist, wrong quotes.

  1. 1
    Ground itGive the model the real source text (RAG) and tell it to answer only from that text.
  2. 2
    Allow “I don’t know”Say explicitly that not knowing is an acceptable answer.
  3. 3
    Lower the temperatureFor factual work. It helps, but does not remove the problem.
  4. 4
    VerifyCheck important facts, numbers and code. Ask for sources and check them.

Knowledge and context limitations

Knowledge cutoff

Knows nothing after its training data ends. Give it a search tool or paste newer facts into the context.

No private data

Hasn’t seen your company files, emails or database unless you provide them.

Context window

Very long documents may not fit, and details in the middle may get less attention.

No memory between chats

The app must send the history every time.

Tokens, not letters

Counting letters in a word or long arithmetic can go wrong.

Sensitive to wording

A small prompt change can change the answer, and answers may vary run to run.

Why you must evaluate outputs

The text is fluent, so a wrong answer is easy to believe, and answers change between runs. So we test the model rather than trust it.

Open vs proprietary models

Now the practical question: which model should we use, and how do we run it? There are two big families.

Open-weight models

The company publishes the weights, so anyone can download them, run them on their own computer or server, and often change them. Examples: Llama, Mistral, Qwen, Gemma, DeepSeek, gpt-oss.

Like getting the finished cake: cut it, decorate it, serve it your way, but you don’t always get the recipe (training data and code).

Proprietary (closed) models

Owned and run by a company. You use them through an API or app; the weights stay secret. Examples: GPT (OpenAI), Claude (Anthropic), Gemini (Google).

Like a restaurant: you order, they cook. Great food without owning a kitchen, but you can’t see how it’s made. Often the strongest and easiest to start with; you pay per token.

Open-weight ≠ open-source You may get the weights without the training data or code. Every model also has a licence, and some limit commercial use. Always read it.

API access vs self-hosting

Customization: start at the top

  1. 1
    PromptingClear instructions and a few examples. Cheapest and fastest. → next note
  2. 2
    RAGGive the model your own documents in the context.
  3. 3
    Fine-tuningTrain the model a little more on your own examples to change its style, format or skill.
  • Open models: full control. Efficient methods like LoRA train only a small add-on, so one GPU can be enough for a small model.
  • Proprietary models: some providers offer fine-tuning for selected models; options are limited and the tuned model stays on their platform.

Infrastructure requirements

An open model must run on GPUs, and the main limit is GPU memory. Rule of thumb for the weights:

memory (GB)  ~  parameters (billions)  x  bytes per number
16-bit = 2 bytes     8-bit = 1 byte     4-bit = 0.5 byte

7B model,  16-bit  ->  7 x 2   = 14 GB
7B model,   4-bit  ->  7 x 0.5 = 3.5 GB
70B model, 16-bit  ->  70 x 2  = 140 GB
  • Quantization stores each number with fewer bits (e.g. 4-bit instead of 16-bit): much smaller model, small loss in quality.
  • Real needs are higher: the model also needs working memory (the KV cache) that grows with context length.
  • A small model (~7–8B) in 4-bit runs on a laptop or home GPU; Ollama and llama.cpp make this easy. For many users at once, servers use tools like vLLM.
  • Beyond GPUs you need storage, serving software, monitoring and a plan for scaling.

Cost: pay-per-use vs fixed

An API is pay-per-use: no usage, no bill. Self-hosting is a fixed cost: the GPU server costs the same busy or idle. With the example numbers from earlier (not real prices):

API per month       = requests/day x cost/request x 30
                    = 10,000 x $0.006 x 30  =  $1,800
Self-host (assumed) = $2,000 per month, fixed

Break-even = 2,000 / (0.006 x 30)  =  about 11,100 requests per day

Below break-even the API is cheaper; above it, self-hosting can win. But count the hidden costs: engineers’ time, monitoring, downtime, and the limit on how many requests one GPU server can handle.

Privacy and data

With an API, your prompts and documents go to the provider’s servers. Check:

  • Does the provider store your data, and for how long?
  • Is it used to train their models? (Business API terms often say no, but read them.)
  • In which country is it processed?
  • Which rules apply? For example GDPR (Europe), the DPDP Act (India), HIPAA (US health data).

Self-hosting keeps data inside your network, but you are responsible for securing it. A middle path is a private deployment of a model inside your own cloud account.

Never paste passwords, secret keys or personal data into any AI tool you haven’t checked.

Key terms

Large Language Model (LLM)
An AI model trained on huge amounts of text to learn language patterns, which takes a prompt and generates a text response.
Token
A small chunk of text (a word, part of a word, a character or punctuation) that a model treats as one unit; roughly 4 characters of English.
Tokenizer
The program that splits text into tokens and maps each token to a numeric ID; each model family has its own, often based on Byte Pair Encoding.
Context window
The maximum number of tokens, input plus output together, that a model can process in a single request.
Embedding
A vector of numbers representing the meaning of a token or text, so that similar meanings have nearby vectors.
Cosine similarity
A measure of how similar two vectors are, based on the angle between them; values near 1 mean very similar meaning.
Transformer
The neural-network design behind modern LLMs, introduced in 2017, which processes all tokens in parallel and relates them using attention.
Self-attention
The mechanism that lets each token weigh and blend in information from the other tokens in the same text, giving it context-specific meaning.
Inference
Using a trained model to generate output for new input; the weights stay fixed and nothing is learned.
Autoregressive generation
Producing text one token at a time, appending each chosen token to the input before predicting the next.
Temperature
A sampling setting that controls randomness: low values almost always pick the top token, high values give less likely tokens more chance.
Top-p (nucleus) sampling
Sampling only from the smallest set of tokens whose probabilities add up to p.
Hallucination
A fluent, confident model answer that is false or made up.
Time To First Token (TTFT)
The delay between sending a request and receiving the first token of the response.
Quantization
Storing model weights with fewer bits (for example 4-bit instead of 16-bit) to cut memory use, with a small loss in quality.

Self-check

Pick an answer. You’ll see right away whether it’s correct and why.

A chat app “remembers” what you said three messages ago. How?

  1. The model updated its weights after each message
  2. The model has a built-in memory per user
  3. The app re-sends the earlier messages inside each new request
  4. The tokenizer stores the conversation

LLMs are stateless between requests. The app puts the history back into the context window every time.

Context window 8,000 tokens; your prompt is 7,600 tokens; the ideal answer needs 1,000 tokens. What happens?

  1. The answer is cut off after about 400 tokens
  2. The model compresses the prompt automatically
  3. The full answer is produced; only input counts
  4. The model answers in 1,000 tokens and drops the system prompt

Input and output share the window: 8,000 − 7,600 = 400 tokens of room. The API will report a stop reason like “length”.

10,000 requests a day, 1,200 input tokens at $2.50/M and 300 output tokens at $10/M. Roughly what is the monthly bill?

  1. $180
  2. $600
  3. $6,000
  4. $1,800

$0.003 + $0.003 = $0.006 per request; × 10,000 = $60/day; × 30 = $1,800.

Why does a token ID alone not tell the model what a word means?

  1. IDs are too large to store
  2. An ID is just a label; nearby IDs need not have related meanings
  3. IDs change every request
  4. IDs only work for English

IDs are like roll numbers. Embeddings provide the meaning, placing similar words close together.

What problem of RNNs did Transformers solve most directly?

  1. RNNs could not use numbers
  2. RNNs had no activation functions
  3. RNNs read one word at a time and forget far-away words
  4. RNNs could not be trained at all

Transformers read all tokens at once (parallel, fast) and let every token attend directly to every other, however far apart.

You are extracting invoice numbers into JSON. Which temperature fits best?

  1. 0 to 0.3
  2. About 0.7
  3. 1.0
  4. 2.0

Extraction and classification want consistent, predictable output, so use a low temperature.

Streaming is switched on. What changes?

  1. The total generation time halves
  2. The first words appear sooner; total time is about the same
  3. Output tokens become free
  4. The answer becomes more accurate

Streaming sends tokens as they’re produced. It improves perceived speed, not total time or quality.

Which is the best first defence against hallucinated policy answers in a support bot?

  1. Set temperature to 0 and trust the result
  2. Use a bigger model
  3. Fine-tune on the internet
  4. Put the actual policy text in the context and tell the model to answer only from it, or say “I don’t know”

Grounding the model in real source text (RAG) and allowing “I don’t know” is the main fix. Low temperature alone does not remove hallucinations.

Roughly how much GPU memory do the weights of a 7B model need at 4-bit?

  1. 0.7 GB
  2. 14 GB
  3. 3.5 GB
  4. 28 GB

7 billion × 0.5 bytes ≈ 3.5 GB, plus extra working memory (KV cache) in practice.

A hospital wants to summarise patient notes, and data must not leave its network. What is a good starting choice?

  1. Any public chatbot website
  2. A self-hosted open model, or a private deployment
  3. The biggest proprietary API with default settings
  4. A rule-based keyword system

Sensitive data that must stay inside points to self-hosting or a private deployment in the customer’s own cloud.

All of it, in one sentence

An LLM turns text into tokens, tokens into embeddings, lets them share meaning through attention, and then predicts one token at a time inside a limited context window; as an engineer you control what goes into that window, how tokens are sampled, and the trade-off between quality, speed and cost.
