Integrating Local Git with Remote GitHub

Put your Git repositories online, collaborate through forks and pull requests, fix merge conflicts, publish a website for free, and do it all from a GUI if you prefer.

What GitHub is

The housing society notice boardEach family keeps its own diary at home (that’s Git on your laptop). But the society has one notice board in the lobby where everyone pins proposals, comments on them and the secretary approves what goes ahead. GitHub is that shared notice board for code: one central place to share repositories, discuss changes and approve them.

GitHub is a platform where you upload a copy of your Git repository (often shortened to repo), hosted on github.com. It does much more than store repos: it makes it easy to collaborate by giving you

  • a central location to share the repository,
  • a web interface to browse code, history and branches, and
  • features like forking, pull requests, Issues, Projects and Wikis to specify, discuss and review changes with your team.
Git vs GitHub Git is the version control tool that runs on your machine. GitHub is a website that hosts Git repositories and adds teamwork features. You can use Git without GitHub, but not the other way round.

Why use GitHub?

GitHub is much more than a place to store repositories. It gives you:

1 · Version control

Built on Git, a powerful distributed version control system: track changes, collaborate and manage project versions effectively.

2 · Documented requirements

Use Issues to record bugs or describe new features you want the team to build.

3 · Independent streams of history

With branches and pull requests, people collaborate on different features at the same time.

4 · Review work in progress

The pull request list shows every feature being worked on. Open one to see the latest changes, the discussion, the status of checks like a Continuous Integration (CI) server, and to add your own review before changes are accepted.

5 · Team progress

The commit history shows what the team has been working on.

6 · Public and private repos

Public repos encourage open collaboration and sharing; private repos keep proprietary or sensitive projects secure.

In the field (FDE) Your GitHub profile is your portfolio. Customers and hiring managers look at public repos, READMEs and how you write PR descriptions. Keep demo projects tidy and documented.

Creating a repository on GitHub

Click the + sign at the top right of any GitHub page (next to your profile picture) and choose New repository. The new-repository form asks for six things:

  1. 1
    OwnerCreate the repo under your own username or under an organisation. If you have no organisation access, leave it as your username.
  2. 2
    Repository nameUse letters, numbers, hyphens, underscores and periods. Any other character is replaced with a hyphen. → e.g. project_html
  3. 3
    Description (optional)A few words about what the repository is for.
  4. 4
    Public or PrivatePublic repos can be viewed by anyone. Private repos can be viewed only by people you invite as collaborators.
  5. 5
    Add a README fileTick the checkbox to start the repo with a README.md that explains the project.
  6. 6
    .gitignore and licensePick a .gitignore template for your language and a license (such as MIT), then click Create repository.
Pushing an existing project? Leave README, .gitignore and license unticked. Otherwise the GitHub repo starts with a commit your laptop doesn’t have, and your first push is rejected until you pull and merge it.

For more on what goes in .gitignore, see the samples in the previous note.

Pushing code to GitHub

Once the repository exists on GitHub, there are two ways to get your code into it.

Way 1 · Start a new project with Git and push it

new project → GitHub
# 1. create a folder "project_html"
mkdir project_html

# 2. move into the project folder
cd project_html

# 3. initialise git
git init

# 4. add code files, then stage and commit
touch index.html          # create the HTML file and add some HTML code
git add .
git commit -m "initial commit"

# 5. connect to the GitHub repo and push
# add a remote named "origin" that points to your GitHub repo
git remote add origin <github_repo_link>

# rename the current branch to "main" (older Git calls it "master")
git branch -M main

# push the local "main" branch to "origin" and set it as upstream
git push -u origin main

Way 2 · Push an existing Git project

You already have a project with staged and committed work. From its root directory:

existing repo → GitHub
# add a remote named "origin" for your local repository
git remote add origin <github_repo_link>

# rename the default branch master to main
git branch -M main

# push the local branch to the remote named origin
git push -u origin main

What those three commands do

CommandMeaning
git remote add origin <url>Saves the GitHub URL under the short name origin, so you don’t type the URL again.
git branch -M mainRenames the current branch to main; -M forces it even if a main already exists.
git push -u origin mainUploads main to origin. -u remembers the link, so next time plain git push is enough.
GitHub shows you these commands A freshly created empty repo displays both recipes, with your repo’s URL already filled in. Copy them from there.
“remote origin already exists” You ran git remote add origin twice, or the repo was cloned. Check with git remote -v; change the URL with git remote set-url origin <new_url>.

Forking an existing repository

Forking creates a copy of someone else’s repository (the upstream repository) under your own GitHub account. This copy, the fork, is an independent repository: you can change, add to and experiment with the code in your fork without affecting the original.

  1. 1
    Open the repository you want to forkOn GitHub, go to the project’s page.
  2. 2
    Click ForkThe button is at the top right of the repository page. Choose your account as owner and click Create fork.
  3. 3
    Find your copyThe fork now appears in your repositories as your-username/project, with a note “forked from owner/project”.

To work on the fork, clone your fork and add the original as a second remote:

# clone your fork (this becomes "origin")
git clone https://github.com/<your-username>/<project>.git
cd <project>

# add the original repository as "upstream"
git remote add upstream https://github.com/<owner>/<project>.git

# check both remotes
git remote -v
origin    https://github.com/your-username/project.git (fetch)
origin    https://github.com/your-username/project.git (push)
upstream  https://github.com/owner/project.git (fetch)
upstream  https://github.com/owner/project.git (push)
Fork or just clone? If you have write access (a teammate added you), clone and push branches directly. If you don’t, as with most open-source projects, fork first: you can push to your fork, and send work upstream with a pull request.

Pull requests (and merge requests)

The leave applicationYou don’t change the office calendar yourself. You write a leave application, your manager reads it, maybe asks a question, and then approves it. A pull request is an application to merge your branch: “here are my changes, please review and pull them in.”

Pull requests are the heart of collaborative development on GitHub. Merge request is simply GitLab’s name for the same thing. After you have forked and cloned the project, follow these steps:

1 · Create a branch

Make a new branch for your feature, bug fix or improvement.

# create a branch
git branch <branch_name>

# switch to it
git checkout <branch_name>

2 · Make changes

Edit the code in your branch. Make sure the changes address the issue or feature you are working on, and nothing else.

3 · Stage and commit

# stage all changes
git add .

# commit them with a clear message
git commit -m "feat: add contact form"

4 · Sync with the original repository

git pull fetches and merges changes from a remote into your local branch. In a fork, plain git pull talks to your fork, so to get the original project’s latest work, pull from upstream:

# bring the original project's latest main into your branch
git pull upstream main

5 · Push the branch

# from your branch: create it on your fork and link it
git push -u origin <branch_name>

6 · Open a pull request

  1. a
    Go to your fork on GitHubA yellow banner usually offers Compare & pull request for the branch you just pushed. Otherwise open the Pull requests tab and click New pull request.
  2. b
    Pick the branchesbase = where the changes should go (e.g. owner/project : main); compare = your branch with the changes.
  3. c
    Describe itGive a descriptive title and a detailed description: what changed, why, and how to test it. Then click Create pull request.

7 · Review and discuss

Invite relevant teammates or the maintainers as reviewers. Discuss the changes and respond to feedback and concerns in the PR’s comments.

8 · Make necessary changes

If reviewers ask for changes, make them on the same branch, commit and push again. The PR updates automatically.

9 · Merge the pull request

Once the PR is approved and all discussions are resolved, a maintainer clicks Merge pull request, and your changes join the original repository.

10 · Delete the branch

After merging, delete the branch (GitHub shows a Delete branch button), and locally with git branch -d <branch_name>.

In the field (FDE) Keep PRs small and focused. A 50-line PR with a clear description and screenshots gets reviewed the same day; a 2,000-line one sits for a week. Link the PR to the customer ticket or Issue it solves.

Handling merge conflicts

A merge conflict happens when two branches change the same lines of a file (or one deletes a file the other edits) and Git cannot decide which version to keep. It shows up during a merge, when Git integrates changes from one branch into another, for example during git pull or git merge. Git stops and asks you, a human, to choose.

Steps to resolve a conflict

  1. 1
    Identify the conflicted filesWhen git pull or git merge hits a conflict, Git says so and lists the files. git status shows them as “both modified”.
  2. 2
    Open the conflicted filesOpen each one in your editor. Git has marked the conflicting sections with conflict markers.
  3. 3
    Resolve the conflictsDecide what the final text should be: yours, theirs, or a mix. Then delete all three marker lines. VS Code offers “Accept Current / Incoming / Both Changes” buttons above each conflict.
  4. 4
    Stage, commit and pushMark each file resolved with git add, finish the merge with git commit, then git push.
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
after you have edited the file
git status                       # lists files still "both modified"
git add index.html               # mark it as resolved
git commit -m "merge: resolve conflict in index.html"
git push
Don’t commit the markers A file that still contains <<<<<<< or >>>>>>> will break your code. Search for them before you commit. Stuck halfway? git merge --abort puts everything back as it was before the merge.

Hosting a website on GitHub Pages

GitHub Pages hosts static websites (HTML, CSS and JavaScript files) directly from a GitHub repository, for free. No server to manage.

  1. 1
    Create a GitHub repositoryMake sure it is public (on a free account, Pages works only for public repos).
  2. 2
    Push your website filesAdd all the HTML, CSS and JavaScript files your site needs. The home page must be called index.html.
  3. 3
    Set up and enable GitHub Pages
    1. a
      Open SettingsClick the Settings tab of the repository you want to host.
    2. b
      Select PagesIn the left sidebar, under “Code and automation”.
    3. c
      Choose the sourceUnder “Build and deployment”, set Source to Deploy from a branch.
    4. d
      Pick the branch and folderSelect the branch (e.g. main) and the folder / (root), then click Save. Wait a few minutes for the site to build.
  4. 4
    Open your web pageThe live link appears at the top of the Pages section: https://<username>.github.io/<repo>/.
Every push redeploys Once Pages is on, each push to the chosen branch republishes the site automatically. A repo named exactly <username>.github.io is served at the root URL https://<username>.github.io/.
In the field (FDE) Pages is perfect for a quick customer demo, a product prototype or your own portfolio. It cannot run server code (Python, databases); for anything with a backend you will need a real host.

Alternatives to GitHub

Several platforms offer similar functionality:

PlatformWhat it offers
GitLabA comparable suite: Git repository hosting, code collaboration and built-in continuous integration (CI). Offers GitLab Pages for website hosting. Calls pull requests “merge requests”.
BitbucketA robust alternative (by Atlassian) with Git hosting, code collaboration and issue tracking. Supports CI through Bitbucket Pipelines, and fits well with Jira.
SourceForgeA long-standing open-source development platform with code hosting, issue tracking and project management. Free for open-source projects, with paid plans for private projects.
LaunchpadA software collaboration platform by Canonical, the company behind Ubuntu. Code hosting, issue tracking and more for open-source projects. Free to use.
GiteaA self-hosted Git service: free, open source, with many of GitHub’s features. A good option for teams who want to run their own code hosting.
In the field (FDE) Enterprise customers often use GitLab (sometimes self-hosted) or Bitbucket instead of GitHub. The Git commands are identical; only the web screens and the words (“merge request”, “pipeline”) change.

GitHub Desktop: what it is and how to install it

GitHub Desktop is a free application that gives Git and GitHub a graphical user interface (GUI). Common operations such as cloning repositories, making and committing changes, and pushing to GitHub become buttons instead of commands.

For beginners

Learn the basics of Git without worrying about the command line.

For experienced users

Speed up the workflow: see diffs visually, pick lines to commit, and collaborate more easily.

Installation

  1. 1
    DownloadVisit https://desktop.github.com and download the version for your operating system (Windows or macOS). The download button is pre-selected for your OS.
  2. 2
    InstallRun the installer and follow the on-screen instructions.
  3. 3
    Launch GitHub DesktopOpen the app after installation.
  4. 4
    Sign inSign in with your GitHub account to access your repositories. You can continue without signing in, but then you can’t publish to GitHub. → you land on the home screen

How to use GitHub Desktop

With a GitHub account and the app installed and signed in, here is the everyday loop, and the Git command each button runs for you:

  1. 1
    Create a new repositoryFile → New repository (or “Create a New Repository on your hard drive” on the home screen). Fill in the name, folder and options, then click Create repository. → git init
  2. 2
    Clone a repositoryClick Clone a repository from the Internet. Search your repositories, select one and click Clone, or open the URL tab and paste a repo link. → git clone
  3. 3
    Create a new branchClick Current Branch at the top to see all branches, then New Branch. Enter the name and click Create branch. → git checkout -b
  4. 4
    Make changes and commitOpen the repo in your editor, edit and save. The changed files and their diffs appear in the Changes list. Type a summary in the box at the bottom left and click Commit to <branch>. → git add + git commit
  5. 5
    Publish to GitHubAfter committing, click Publish branch (first time) or Push origin in the top bar. → git push
  6. 6
    Pull changes from GitHubWhen others have pushed, click Fetch origin to check, then Pull origin to bring the updates in. → git fetch / git pull

Repeat this loop until the project is done: edit, commit, push, and pull your teammates’ work as you go.

Key terms

GitHub
A website that hosts Git repositories and adds collaboration features such as pull requests, Issues, Projects, Wikis and GitHub Pages.
Repository (repo)
A project folder tracked by Git, including all its files and full history; on GitHub it also has its own web page.
origin
The default name for the main remote repository your local repo pushes to and pulls from, usually your copy on GitHub.
upstream
By convention, the remote name for the original repository you forked from, used to pull in the project’s latest changes.
Fork
Your own independent copy of someone else’s repository under your GitHub account, which you can change without affecting the original.
Pull request (PR)
A request to merge the commits from one branch into another, with a place for review, discussion and automated checks before merging.
Merge request (MR)
GitLab’s name for a pull request; it works the same way.
Merge conflict
What happens when two branches change the same lines and Git cannot combine them automatically, so a person must choose the final content.
Conflict markers
The lines <<<<<<<, ======= and >>>>>>> that Git writes into a file to show the two competing versions of a conflict.
GitHub Pages
GitHub’s free hosting for static websites, served straight from a branch of a repository at username.github.io/repo.
README.md
A Markdown file at the root of a repo that explains the project; GitHub shows it on the repository’s front page.
GitHub Desktop
A free graphical app for Windows and macOS that performs common Git and GitHub operations with buttons instead of commands.

Self-check

Pick an answer. You’ll see right away whether it’s correct and why.

What is the difference between Git and GitHub?

  1. They are two names for the same tool
  2. GitHub runs on your laptop; Git is a website
  3. Git is the version control tool; GitHub hosts Git repos and adds collaboration features
  4. Git only works with GitHub

Git tracks history on your machine. GitHub is a hosting platform built around Git.

What does git remote add origin <url> do?

  1. Saves the URL under the short name origin
  2. Uploads all your commits
  3. Creates a repository on GitHub
  4. Renames your branch to origin

It only registers a remote. git push is what actually uploads.

What does the -u in git push -u origin main do?

  1. Undoes the last push
  2. Links local main to origin/main, so plain git push works next time
  3. Pushes only updated files
  4. Makes the repo public

-u sets the upstream (tracking) branch.

You forked a project. Which command brings the original project’s latest main into your branch?

  1. git pull
  2. git push upstream main
  3. git clone origin
  4. git pull upstream main

In a fork, origin is your copy. The original is the upstream remote you added.

In a pull request, what is the base branch?

  1. The branch with your new changes
  2. The branch the changes should be merged into
  3. The oldest branch in the repo
  4. A backup of main

Base is the destination (often main); compare is the branch carrying your changes.

In a conflicted file, which part is the incoming branch’s version?

  1. Between <<<<<<< HEAD and =======
  2. Above <<<<<<< HEAD
  3. Between ======= and >>>>>>>
  4. Below >>>>>>>

HEAD (your current branch) comes first; the incoming branch’s text sits after the ======= divider.

You’ve edited a conflicted file into its final form. What next?

  1. git add the file, then git commit
  2. Delete the branch
  3. Run git init
  4. Nothing, Git detects it automatically

git add marks the conflict resolved and git commit completes the merge.

Which site can GitHub Pages host?

  1. A Django app with a database
  2. A Node.js API server
  3. A private site on any free account
  4. A static HTML, CSS and JavaScript site

Pages serves static files only; it runs no server code, and free accounts need a public repo.

In GitHub Desktop, which button does the same job as git push?

  1. Fetch origin
  2. Current Branch
  3. Push origin / Publish branch
  4. Commit to main

Push origin (or Publish branch the first time) uploads your commits; Fetch origin only checks for new ones.

All of it, in one sentence

GitHub hosts your Git repos: connect with git remote add origin and git push -u, contribute by forking, branching and opening a pull request, fix merge conflicts by choosing between the markers, publish static sites with GitHub Pages, and use GitHub Desktop when you’d rather click than type.
