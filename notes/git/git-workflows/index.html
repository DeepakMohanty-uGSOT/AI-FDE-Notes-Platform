Local Git Deep Dive

Use Git the way you will on the job: start a new project, put an existing one under version control, join a teammate’s project, and keep junk and secrets out with .gitignore.

Three ways you meet Git

The family photo albumSometimes you buy a fresh album for a new trip. Sometimes you find a shoebox of old photos and finally put them into an album. And sometimes your cousin hands you the family album and asks you to add this year’s pictures. Git projects start the same three ways: brand new, already existing, or someone else’s that you join.

This note strings Git commands together into the real workflows you will repeat every week.

Before you start Make sure Git is installed and configured on your system (git --version, plus user.name and user.email set with git config). The next note shows the setup step by step.

Using Git in a brand-new project

Starting from scratch means you set up version control on day one: create the folder, create a repository, then commit as you go so the project’s whole history is recorded.

  1. 1
    Create a project folderMake it in File Explorer (Windows) or Finder (Mac), or from the terminal. → mkdir, cd
  2. 2
    Initialise the local repositoryRun git init inside the folder. Git creates a hidden .git folder that stores all history. → git init
  3. 3
    Create files and write some codeHere, a small Java program.
  4. 4
    Check, stage and commitLook with git status, stage with git add, save with git commit. → repeat as you work

1 · Create the project directory

# create a folder "project_java"
mkdir project_java

# move into the project folder
cd project_java

2 · Initialise the local Git repository

# initialise git
git init
Initialized empty Git repository in /home/you/project_java/.git/

3 · Create a file and write some code

MyFirstProgram.java
class MyFirstProgram {
    public static void main(String[] args) {
        System.out.println("Hello, World");
    }
}

4 · Check status, then stage and commit

Before staging, it is good practice to run git status and see what Git currently knows about:

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        MyFirstProgram.java

nothing added to commit but untracked files present (use "git add" to track)

The new file is untracked. Stage it and make your first commit:

# stage everything in the folder
git add .

# commit with a message
git commit -m "initial commit"

From here, you keep working, staging with git add and committing with git commit. Use git log any time to see the commit history:

# view commit history
git log
commit 3f2a9c1d8e7b6a5f4e3d2c1b0a9f8e7d6c5b4a39 (HEAD -> main)
Author: Your Name <you@example.com>
Date:   Tue Oct 13 10:15:42 2026 +0530

    initial commit
master or main? Older Git versions name the first branch master; newer setups use main. Your git status shows whichever your Git uses. Set your default once with git config --global init.defaultBranch main.

Using Git in an existing project

Suppose you already have a project, say an online shop in a folder called Ecom, and it has never used version control. You can add Git at any time; your files stay exactly where they are.

  1. 1
    Go to the project root directoryThe top-level folder that contains everything. → cd Ecom
  2. 2
    Initialise the repositoryCreates the .git folder inside Ecom. → git init
  3. 3
    Stage and commit all project filesYour first commit captures the project as it is today. → git add . · git commit
# 1. suppose the project root directory is "Ecom"
cd Ecom

# 2. initialise git (creates the .git repository)
git init

# 3. stage all files, then commit them with a message
git add .
git commit -m "initial commit"

After that, repeat step 3 as you work: stage and commit with a meaningful message each time.

Write the .gitignore first In an old project, git add . grabs everything: node_modules, build output, log files and even a .env full of passwords. Create a .gitignore before your first git add ., and check git status before committing.

Joining an existing Git project

Imagine your friend has invited you to contribute to their Git project. Their repository lives on a hosting platform, and you need a copy on your laptop, a branch of your own, and a way to send your work back.

1 · Get the project URL

Get the URL of the existing repository from its hosting platform, such as GitHub, GitLab or Bitbucket.

GitHub, GitLab and Bitbucket are popular web platforms that host Git repositories. They add collaboration, review and project-management tools on top of Git. The next note covers GitHub in depth.
# a GitHub repository URL looks like
https://github.com/<owner>/<projectFolder>.git

2 · Clone the repository

# clone the repository
git clone <projectGitURL>

3 · Move into the project directory

cd <projectFolderName>

4 · Create and switch to a new branch

# make sure you are on the main branch first
git checkout main

# create a new branch
git branch feat/hero-section

# switch to the newly created branch
git checkout feat/hero-section

The shortcut git checkout -b feat/hero-section (or git switch -c feat/hero-section) does both in one step.

5 · Work

Make your changes: add features, fix bugs, improve the code.

6 · Stage and commit

# stage
git add .

# commit
git commit -m "fix: hero icon fix"

7 · Pull (optional, but a good habit)

Before pushing, pull the latest changes from the remote repository. Pulling first means you are working on the latest code and helps you catch conflicts on your laptop instead of on the server.

# bring in the latest main and merge it into your branch
git pull origin main

8 · Push

Now send your commits to the remote repository. The very first push of a new branch must tell Git where the branch should go:

# first push of this branch: create it on origin and remember the link
git push -u origin feat/hero-section

# every later push from this branch
git push

Once your commits are pushed, it is up to the project owners to review and merge your branch, usually through a pull request.

git clonegit checkout -bworkgit addgit commitgit pullgit push
“has no upstream branch” A plain git push on a brand-new branch fails with fatal: The current branch feat/hero-section has no upstream branch. Use git push -u origin <branch> once; after that, plain git push works.
In the field (FDE) On a customer engagement you usually join their repository. Never commit straight to main: work on a branch named for the task (feat/…, fix/…), pull often, and let their team review before it merges. It builds trust fast.

What .gitignore does

The suitcase listPacking for a trip, you don’t carry the dustbin, yesterday’s newspaper or the house keys you must leave with your neighbour. You keep a “don’t pack” list on the fridge. .gitignore is Git’s “don’t pack” list: files that may sit in your folder but must never go into the repository.

The .gitignore file is a plain-text configuration file in your repository that lists files, folders or patterns Git should ignore when tracking changes. Git reads it to decide which files should not be included in version control, even though they are present in the project folder.

Two tiny examples

.gitignore · one file
# ignore a specific file
.env
.gitignore · several entries
# ignore multiple files and folders
node_modules
build/

Put the file in the root of the repository, named exactly .gitignore (with the leading dot, no extension), and commit it so everyone on the team shares the same rules.

Why .gitignore matters

1 · No versioning of unnecessary files

Compiled binaries, log files and temporary files are created during development. They are not needed in version control and can be large. Ignoring them avoids storing useless versions and saves space.

2 · A cleaner repository

With non-essential files left out, the repo stays focused on source code and configuration, so it is easier to navigate and manage.

3 · No leaked secrets

It helps stop sensitive data such as API keys, passwords and other confidential information from being accidentally committed and shared.

4 · Consistency across platforms

Each OS and IDE creates its own files (.DS_Store, Thumbs.db, .idea/). Ignoring them keeps the repo the same for developers on different machines.

5 · Better performance

Leaving out large or numerous files makes Git operations such as clone, pull, push and branching faster.

.gitignore does not untrack files It only affects files Git is not already tracking. If you committed .env before adding it to .gitignore, stop tracking it with git rm --cached .env and commit. The file stays on your disk.
In the field (FDE) A customer’s API key pushed to a repo is a security incident, even if you delete it in the next commit: it is still in the history. If it happens, rotate the key immediately, then clean up. Keep secrets in .env, ignore it, and commit a .env.example with blank values instead.

Pattern rules and sample .gitignore files

How patterns work

PatternWhat it ignores
# commentNothing. Lines starting with # are comments.
.envAny file or folder named .env, at any depth.
build/Folders named build (the trailing / means “folder only”).
*.logEvery file ending in .log. * matches any characters.
/config.localOnly config.local in the repository root (leading /).
**/temptemp in any folder, however deep.
!keep.logAn exception: do track keep.log, even though *.log is ignored.

Don’t write it from memory GitHub can add a ready-made .gitignore for your language when you create a repository, and the github/gitignore repository has templates for almost every stack. Start from one and edit it.

Check that a file is really ignored

git check-ignore -v .env      # prints the .gitignore line that matches
git status --ignored          # lists ignored files too

Key terms

git init
Turns the current folder into a Git repository by creating a hidden .git folder that stores the project’s history.
Project root
The top-level folder of a project, where .git and .gitignore live.
Untracked file
A file in the project folder that Git has never been told to track; it appears under “Untracked files” in git status.
git clone
Copies a remote repository, with all files, history and branches, onto your machine and sets up a remote named origin.
Feature branch
A branch created for one task, such as feat/hero-section, so the work stays separate from main until it is reviewed and merged.
Upstream branch (tracking)
The remote branch a local branch is linked to, set with git push -u, so plain git push and git pull know where to go.
.gitignore
A text file in the repository listing files, folders and patterns that Git should not track, such as dependencies, build output, logs and secrets.
Ignore pattern
A line in .gitignore such as *.log, build/ or !keep.log that matches files to ignore or, with !, to re-include.
git rm --cached
Stops Git tracking a file that was already committed, while leaving the file on disk. Used when you ignore a file too late.

Self-check

Pick an answer. You’ll see right away whether it’s correct and why.

You have an old project folder with no version control. What is the first Git command to run inside its root?

  1. git clone
  2. git init
  3. git push
  4. git commit

git init creates the .git repository in an existing folder. git clone is for copying a repository that already exists somewhere else.

Right after creating MyFirstProgram.java in a new repo, how does git status describe it?

  1. Staged
  2. Committed
  3. Untracked
  4. Ignored

Git has never been told about the file, so it is untracked until you git add it.

Your friend invites you to their repo. Which order is right?

  1. push → clone → branch → commit
  2. branch → clone → push → commit
  3. clone → commit on main → push to main
  4. clone → branch → commit → pull → push

Copy the project, work on your own branch, commit, bring in the latest changes, then push your branch for review.

You run git push on a brand-new local branch and get “has no upstream branch”. What fixes it?

  1. git push -u origin <branch>
  2. git init again
  3. Deleting the branch
  4. git commit --amend

The remote doesn’t know the branch yet. -u origin <branch> creates it there and links the two, so later pushes need no arguments.

Why pull before you push?

  1. Pushing is impossible without a pull
  2. To work on the latest code and resolve conflicts locally first
  3. Pull deletes old branches
  4. Pull creates the .gitignore

Pulling brings in teammates’ commits so any clash is found and fixed on your machine before you push.

You added .env to .gitignore, but Git still shows changes to it. Why?

  1. The file name needs a *
  2. .gitignore only works after a push
  3. It was already tracked before it was ignored
  4. Hidden files cannot be ignored

.gitignore only affects untracked files. Run git rm --cached .env and commit to stop tracking it.

Which line ignores every log file but keeps keep.log?

  1. log/ then keep.log
  2. *.log then #keep.log
  3. /*.log only
  4. *.log then !keep.log

*.log ignores all log files and !keep.log adds an exception. A # line is just a comment.

Which is not a reason to use .gitignore?

  1. To delete files from your disk
  2. To keep API keys out of the repository
  3. To speed up clone and push
  4. To avoid OS and IDE clutter like .DS_Store

Ignored files stay on your disk. .gitignore only controls what Git tracks.

All of it, in one sentence

Start a project with git init (new or existing) or git clone (joining), then loop through branch, add, commit, pull, push, and keep dependencies, build output, logs and secrets out of history with a .gitignore written before your first commit.
